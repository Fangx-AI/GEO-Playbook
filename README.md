## 01 · GEO 基础

GEO 在本项目中指：围绕生成式搜索中的内容发现、准确理解、引用和用户行动，开展内容与技术改进，并用可复查的方法测量结果。它与 SEO、内容策略、信息检索和评估有交集；不要求你先学会训练模型。

### 先分清六件事

- **抓取**：系统能否取得页面；网页能在你浏览器打开，只能说明一种访问条件。
- **索引与检索**：内容是否进入可搜索集合，以及是否为当前问题被选为候选。两者分开排查。
- **生成与引用**：模型形成回答与标注来源；正文提及品牌、引用官网、推荐产品是三个不同事件。
- **用户任务**：读者此刻想完成什么，例如理解概念、比较选项、确认价格或解决故障。
- **可核查证据**：结论对应的事实、原始数据、时间、对象和限制。让人能检查，而不只是读起来可信。
- **效果测量**：把提及、引用、点击、有效咨询分别记录。某一层改善，不自动说明其他层改善。

📚 **Resources**

- [Google：How Search Works](https://developers.google.com/search/docs/fundamentals/how-search-works) — 官方指南 · 英文 / 可切中文 · 入门。先分清抓取、索引、展示，学会定位问题发生在哪一步；不是其他平台内部实现的完整说明。
- [Google：SEO Starter Guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide) — 官方指南 · 英文 / 可切中文 · 入门。重点读页面组织、帮助发现、内容质量和用户体验，用于建立站点基本功。
- [Introduction to Information Retrieval](https://nlp.stanford.edu/IR-book/) — 作者公开教材 · 英文 · 进阶选读。优先选第 8 章检索评估、第 19—21 章网络搜索；无需从第一章一直读完。该资源入口与目录已读，未逐章审阅全书。
- [GEO 原论文与后续研究导读](#research) — 想知道术语来源及实验如何设计，再进入这一节。

**小练习：** 用同一个真实需求分别进行普通搜索和 AI 联网问答，保存各自可见结果；打开 AI 引用的三个来源，标注“是否支持对应句子、是否是原始来源、是否过期”。看不到内部检索过程时写“未知”。这一轮只做理解练习，不据此宣布优化有效。

## 02 · GEO 实践

先选项目，再补通用能力。网站、小程序和独立产品分别有完整操作路线；行业章节处理商品、地域、采购和内容形态的不同约束。每轮先交付一个可检查的结果。各课的虚构产品与服务只用于练写作、计算或给定资料后的匹配判断；实际联网测量必须换成真实对象。没有自己的项目，可用[真实 Notion 文档观察课](#china-observation-lab)。

<a id="content"></a>

### 1. 把用户问题变成一页能用的内容

**要解决的问题**：页面写了很多“领先、强大、可靠”，买家仍不知道是否适合、多少钱、怎样开始。

这一课从 16 道采购问题出发，给出完整事实资料包、可复制 prompt、改前改后全文与人工审核。练习产品为虚构，先学会方法，再替换为自己的真实资料。

![从抽象宣传到明确事实的五组改稿示例；虚构教学产品](assets/content-before-after.png)

**完成标志**：陌生读者能判断适用性、重算费用、找到迁移限制；每项事实都能追到依据。

📚 **Resources**

- [GOV.UK 用户研究](https://www.gov.uk/service-manual/user-research/plan-user-research-for-your-service) — 学会从用户任务出发；用于问题研究，不是 AI 排名指南。

- [Google 组织信息](https://developers.google.com/search/docs/appearance/structured-data/organization) — 核对品牌、公司、产品的真实关联与消歧字段。

#### 动手做：把一段产品广告改成能帮助买家决策的页面

这一课交付四件东西：**采购问题表、证据表、改稿、逐句审核记录**。不用先买监测软件，拿任意一个文本模型就能练。写作任务约 60—90 分钟；产品事实核对的时间另算。

**练习产品“拾页知识库”及其价格、版本、测试记录均为虚构。** 下方所有产品事实都是本课提供的演示资料，不是对市场上同名产品的介绍。你可以直接复制练习；用于自己的项目时，先把整份资料替换为经过负责人确认的真实材料。

##### 第一步：不要从“写一篇 GEO 文章”开始，从买家的原话开始

假设你负责一家团队知识库产品的网站。买家要决定的是能不能用、迁移麻不麻烦、花多少钱、能否带走资料。下面是**仿照采购场景写出的提问示例**，没有冒充真实访谈记录，也没有搜索量数据。

| ID | 保留完整原话的题目示例 | 买家正在做的决定 |
| --- | --- | --- |
| Q01 | 我们 20 人做客服，资料散在 Word 和网盘里，有必要买知识库吗？ | 是否有需求 |
| Q02 | 我们有 300 人，而且必须内网部署，拾页能用吗？ | 是否适用 |
| Q03 | 拾页知识库 20 人一个月一共多少钱？ | 预算 |
| Q04 | 下个月加到 25 人，费用怎么算？ | 增购 |
| Q05 | 299 元是每个人的价格，还是整个团队的价格？ | 计费口径 |
| Q06 | 跟我现在的网盘相比，换工具之前应该试哪些东西？ | 是否值得换 |
| Q07 | 能把其他工具导出的 Markdown 导进去吗？图片怎么办？ | 导入 |
| Q08 | 扫描版 PDF 能不能直接搜索正文？ | 文件兼容 |

| Q10 | 不续费时能否把文档和附件拿走？ | 退出成本 |
| Q11 | 导出之后，评论、历史版本和权限能一起迁走吗？ | 迁移损失 |

真实项目从客服工单、销售记录、站内搜索或访谈取 20 条起步，每条另外保留日期、来源编号、脱敏原话和角色。**“模型觉得用户会问”只能进入候选题，不能填进“真实用户提问次数”。** 同一个客户连续追问三次，也不等于三个客户。

先按“要做的决定”分组，再决定页面。不要给每个同义问句生成一篇文章：

| 题组 | 题目 | 页面归属 | 为什么这样合并 |
| --- | --- | --- | --- |
| 是否适用 | Q01、Q02、Q06 | 选型 / 适用场景页 | 一起回答谁值得试、谁应排除 |
| 多少钱 | Q03—Q05 | 价格页 | 单位和加人规则必须放在同一处 |
| 迁入与故障 | Q07—Q09 | 导入帮助页 | 支持格式与失败原因不能分家 |
| 能否迁出 | Q10、Q11 | 导出帮助页 | “能导出”必须同时交代丢什么 |
| 权限与公开 | Q12、Q13 | 权限说明页 | 目录可见性和公开链接是两个开关 |
| 部署与数据 | Q14、Q15 | 部署 / 数据说明页 | 交给对应事实负责人审查 |
| 账号集成 | Q16 | 集成说明页 | 没有资料就先进入待确认清单 |

本轮只改一页“20 人团队选型说明”，优先回答 Q02—Q05、Q08、Q11、Q14。图片导入、搜索故障、不续费后的导出权限等问题，当前资料不足，留给补证后的帮助页；不假装这篇短稿已经回答全部 16 题。

##### 第二步：先给模型资料包，别让它替产品经理发明功能

下面的 F 编号表示**本课虚构资料卡**，方便练习追踪句子依据。真实工作里，每行应指向可复查的文档版本、截图、合同条款或测试记录；“销售说应该支持”不足以填成“已确认”。

| 证据 ID | 本课允许使用的事实 | 演示中的资料归属 | 发布处理 |
| --- | --- | --- | --- |
| F01 | 拾页知识库 v1.4 是云端团队文档工具；不提供私有化 / 内网部署 | 产品规格卡，2026-10-14 | 可写；部署限制跟结论一起出现 |
| F02 | 团队版每月 299 元含 20 个成员席位、100 GB 存储；额外席位每个每月 20 元 | 价格卡，2026-10-14 | 可写；不自行补税费、折扣、退款规则 |
| F03 | 支持 Markdown、HTML、文本型 PDF；单文件不超过 20 MB；无 OCR | 导入规格卡 v1.4 | 可写；扫描件不能写成“全面兼容 PDF” |
| F04 | 管理员可导出 ZIP，含 Markdown 正文和原始附件；不含评论、历史版本、权限配置 | 导出规格卡 v1.4 | 可写；与“数据可带走”放在一起 |
| F05 | 有目录级成员权限；公开链接默认关闭，管理员可以开启 | 权限规格卡 v1.4 | 可写；不能推成“绝不会外泄” |
| F06 | 演示测试包有 20 个小于 20 MB 的文件：10 个 Markdown、8 个文本型 PDF、2 个扫描 PDF；前 18 个导入成功并能搜索正文，2 个扫描件不能搜索正文 | 人工编制的教学测试记录，非真实实测 | 只演示检查方法；不能当客户成功率 |
| F07 | 未提供文档是否用于模型训练、存储地点、删除保留期的已确认说明 | 待负责人确认 | 不得写“绝不训练”“数据永久删除”等承诺 |
| F08 | 未提供 SSO 支持范围；没有已核准的竞品比较数据 | 待产品负责人确认 | 不得写“全面集成”或“比某某更安全” |

先做两个小计算：20 人是 **299 元 / 团队 / 月**；25 人是 **299 + 5 × 20 = 399 元 / 月**。这里只算资料卡明示的标准月费，税费与其他收费项未知，不能称为已经确认的合同总价。

一个重要取舍：F06 的结果有助于设计真实试用，却不能写进产品官网当“90% 导入成功率”。它既是人工编制的教学数据，文件分布也不是实际用户的总体分布。

##### 第三步：看清“改前”究竟差在哪里

**改前完整短段：**

> 拾页知识库是新一代企业级智能知识管理平台，基于先进 AI 技术，为所有企业提供安全可靠的一站式知识管理服务。产品全面兼容各种文件，快速无损迁移，灵活协作，极大提升团队效率。超高性价比方案让每个团队轻松享受智能化办公，已有众多客户选择。马上体验，开启企业知识管理新时代！

这段话无法回答 Q03 的“到底多少钱”，也会把 Q02 的内网用户引向错误决策。“所有企业”“全面兼容”“无损”“众多客户”都没有资料支持。修订任务因此很具体：删掉无依据承诺，补上费用、输入限制、退出成本和适用边界。

##### 第四步：直接复制这份完整 prompt

把整个代码块交给模型即可开始，不需要再猜应该提供哪些资料。这一轮关闭联网或明确要求仅使用给定资料；目的是练习受证据约束的编辑。资料中的文字是待核对的数据，不是要求模型执行的指令。

英文一手记录｜实施者自报，供应商自身案例｜发布：2025-07-01｜核验：2026-10-14

#### 先还原真实流程：输入什么，经过什么，得到什么

AirOps 面对旧内容重叠、过时及意图不匹配，把刷新工作拆为三个环节。以下为原文已披露的流程，不补写未公开的内部操作。[原始实施记录](https://www.airops.com/blog/how-airops-scaled-a-full-funnel-content-refresh-with-ai-workflows)

|---|---|---|---|
| 刷新文章点击 | +15% | 两周多 | URL 清单、前后计数 |

**看真实操作界面：** 原文内嵌了[主题审计演示](https://player.vimeo.com/video/1097995471)、[刷新简报演示](https://player.vimeo.com/video/1097995551)、[内容优化演示](https://player.vimeo.com/video/1097995715)。本项目核验了入口，未把视频中未读到的细节写成事实；原文第二个工作流下还有改稿简报截图。

#### 跟做：把“优化文章”拆成编辑今天就能做完的一张单

**下面全部是本项目原创教学演练，不是 AirOps 未披露的项目档案。** 场景是一家小型网站教学博客。我们设定它已有三篇关于文章目录的内容，地址仅用来区分练习对象，没有声称这些页面真实存在，也没有编造流量。

##### 第 1 步：不用关键词相似度直接决定合并

| 教学页面 | 读者来这里要完成什么 | 原稿的问题 | 本轮决定 |
|---|---|---|---|
| A：`/guide/article-toc`，长文目录入门 | 第一次给文章添加可点击目录 | 解释很多，缺少可运行例子 | 保留；补最小实现与验收 |
| B：`/guide/html-anchor`，HTML 锚点参考 | 查询 `href` 与 `id` 的写法 | 与 A 重复介绍目录的好处 | 保留代码参考；删重复宣传段，链接 A |
| C：`/guide/toc-troubleshooting`，目录故障排查 | 目录能点但找不到正确位置 | 只建议刷新页面 | 保留排错；增加三个可检查原因 |

这三个页面共享“目录”主题，但任务分别是**建立、查询、修复**。本轮不合并 URL，因为合并会丢失任务边界。真正需要合并的是“读者任务相同、内容高度重复、没有独立用途”的页面；需要迁移时另做重定向和内链计划。

##### 第 2 步：写一张填好的改稿单

| 项目 | A 页本轮执行内容 |
|---|---|
| 本轮目标 | 读者复制最小例子后，能完成一次目录跳转 |
| 原段落 | “合理的目录有助于用户体验，也有助于搜索引擎理解文章。” |
| 具体缺口 | 没有说明目录链接和目标标题怎样对应；没有操作后检查办法 |
| 新增材料 | 一个完整 HTML 例子、两个正确跳转结果、三个故障检查点 |
| 事实依据 | MDN 的链接元素与 `id` 属性文档，见下方 |
| 删除内容 | 没有证据的“添加目录必然获得 AI 引用”承诺 |
| 本轮边界 | 不改 URL、页面标题、其他主题正文；避免把多项变化绑在一起 |
| 验收 | 两个链接分别到达正确标题；目标 `id` 不重复；手机也可操作 |

##### 第 3 步：把抽象段落改成能直接用的内容

下面是 A 页可以新增的原创教程段落：

> **如何让目录跳到正文的对应位置？** 给目标标题设置唯一的 `id`，再把目录链接的 `href` 写成 `#` 加这个值。例如，目录中的 `href="#check"` 对应正文的 `id="check"`。两者拼写必须一致。

```html
<nav aria-label="文章目录">
  <ul>
    <li><a href="#create">创建目录</a></li>
    <li><a href="#check">检查跳转</a></li>
  </ul>
</nav>

<h2 id="create">创建目录</h2>
<p>先给正文标题设置唯一标识，再添加指向它的链接。</p>

<h2 id="check">检查跳转</h2>
<p>点击每一项，确认地址片段和实际到达的标题一致。</p>
```

依据：[MDN 链接元素](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/a)、[MDN 的 id 属性](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/id)。代码是本项目自写。

接着补三个常见排查动作：

1. 点“检查跳转”仍到错误章节：核对 `href` 与目标 `id` 是否一致；不要只看文字相似。
2. 两个目录项都跳到同一处：搜索 HTML 中是否有重复 `id`，使每个目标唯一。
3. 地址栏变化了，但看不清目标：实际检查视口位置；若标题被固定导航遮挡，再调整滚动间距并复测。

这段改稿的价值可以立即检验：读者能完成动作，编辑能测试正确性。至于 AI 引用是否变化，必须另行测量。

##### 第 4 步：把模型限定为“给编辑列任务”，而非替你猜后台数据

以下提示词可以配合完整正文和资料使用：

```text
你是内容编辑。目标读者是第一次给文章添加目录的站长。
本页唯一目标：让读者完成一次可点击的目录跳转。

我会提供页面正文、相邻页面摘要和已核实的文档摘记。
请输出最多三条改稿任务，每条包括：
1. 需要修改的原段落；
2. 读者具体卡在哪里；
3. 可直接插入的新段落或例子；
4. 所依据的已提供资料；
5. 编辑怎样验收。

约束：不要推测流量、引用率或产品能力；
资料不足时标出具体缺失事实；
不要修改 URL，不把相邻页面承担的任务全部搬进来；
删掉“肯定提升 AI 排名”等无证据承诺。
```

##### 第 5 步：让“内容交付完成”和“观察到增长”分别验收

先交付可检查的产物：三页任务表、A 页前后差异、实际跳转截图、事实链接、编辑审核记录。没有网站也可以完成这一步，在本地 HTML 中演示；此时不宣称做出了 GEO 增长。

有可测网站时，再冻结 6 个与三页对应的问题，例如“长文怎样添加目录”“目录链接为什么跳错位置”；保持平台、联网条件、语言和提问频次一致，分别保存发布前与发布后回答。一次回答没有引用你的站点，记录为零；请求失败记录为失败，不和零混算。完整窗口结束后，分别统计提及、引用、引荐访问和业务事件。

**这节学会的具体能力：** 给页面分配任务，拿事实写改稿单，把抽象建议改成可测试内容，保留变化证据。它不是一份“复制就能增长 20%”的配方。

选一个真实服务，例如“面向小型跨境电商的客服系统”。从访谈、售前邮件和客服记录提取 12 个实际问题，分为选型、比较、实施、限制四组，每组 3 题。保存原始问法及来源，删除个人信息。先固定问题集，再测试，避免事后只保留表现好的问题。

##### 第二步：建立两周基线

选 4 篇任务相近的已有页面，2 篇准备修改，2 篇暂不修改。每周在相同产品、语言、地区和联网条件下重复观察，保存完整答案与来源 URL。分开统计“提到品牌”“引用自有域名”“正确描述适用条件”，不把三者合成一个好看的分数。同步记录各页的访问、有效咨询和 SQL；样本很小时保留原始数量。

##### 第三步：制作一份能核验的定位事实表

逐项填写目标用户、适用任务、前置条件、价格适用范围、实施成本、能力限制与证据链接。让熟悉产品的人审核。不能证实的描述删除或标明未知；不要把“适合所有企业”换成另一个无法证明的超级词。

##### 第四步：只改目标两页，留存差异

用事实表改清开头的对象与问题，在读者做决策的位置补充限制、比较维度和证据。保留必要背景，不机械规定必须 150 字或每段两行。记录每项改动、发布时间及实际再次抓取证据；同期尽量不更换域名、重做导航或开启大规模推广，无法避免的变化写进日志。

##### 第五步：继续观察四周并核对业务链路

按基线口径复测，逐条核对引用是否真的支持答案。咨询表单可增加可选的“最初从哪里了解到我们”，但将用户回忆与分析工具来源分开。由销售按事先定义的标准确认 SQL，不因为来源是 AI 就放宽标准。检查新增线索是否重复、垃圾或已经存在于 CRM。

##### 第六步：写出有边界的结论

并列展示改动页与未改动页的前后数量、正确描述率和有效咨询数，再列出产品更新、季节性与平台波动。若只改善描述准确度，就报告这一结果；没有变化也保留。小样本或非随机分组只能提供探索性证据，不能宣布某种句式获得了通用排名优势。

**验收产物：** 固定问题集、四页修改前快照、事实表、改动记录、完整答案与引用、线索去重表，以及一页解释“观察到什么、不能证明什么”的实验结论。

</details>

### 2. 网站如何做 GEO

**要解决的问题：** 官网已经上线，AI 却找不到、引用旧内容，或把产品说错。

**适用对象：** 新站、已有内容站、WordPress / Webflow / 自建站、JavaScript 应用。

**先准备：** 网站修改权限、一个真实业务页面、目标平台，以及能核对的产品事实。

**本周交付：** 一份访问诊断、一个改好的页面、一张发布前基线表。

**从这里动手：** 先检查页面拿到的是什么，再决定改技术还是改内容。

<details>
<summary>展开网站教程：诊断命令 → 页面改造 → 7 天执行 → 故障排查</summary>

#### 第一步：按网站当前状态选入口

| 当前情况 | 第一件事 | 先不要做什么 |
| --- | --- | --- |
| 新站，只有首页 | 做出一页能回答真实选购问题的产品 / 服务说明，从首页直接链接过去 | 不必先批量生成几百篇博客 |
| 老站，有收录和搜索访问 | 从已有访问、销售常发的页面里选一个重要但回答不完整的页面 | 不要一上来全站换 URL、重写全部内容，失去对照 |
| React / Vue 等 JS 站 | 对照原始 HTML、浏览器渲染后正文和目标平台的实际表现 | 不把“用了 React”直接判为无法抓取 |
| 只有登录后应用 | 把可公开的产品说明、帮助、价格、限制放到无需登录的地址 | 不公开用户文件、账户页和私人工作区 |
| 能搜到但 AI 回答错误 | 找到错误句对应的引用来源，核对旧价格、旧版本和同名产品 | 不只在首页增加一句“我们是最好的” |

下面以**虚构的会议室预订网站**为教学对象。域名、路径与页面事实都是示例；把命令中的 URL 改成自己的公开页面。命令使用 Windows PowerShell 中的 `curl.exe`，避免旧版 PowerShell 的 `curl` 别名歧义。

#### 第二步：取得真实响应，留下修复前证据

在项目目录执行；脚本只下载公开页面，输出文件放在新建的时间戳文件夹中：

```powershell
$geoUrl = 'https://example.com/meeting-rooms/small-team'
$geoOrigin = ([uri]$geoUrl).GetLeftPart([System.UriPartial]::Authority)
$geoAuditDir = Join-Path (Get-Location) ('geo-audit-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
New-Item -ItemType Directory -Path $geoAuditDir | Out-Null
$geoHeaders = Join-Path $geoAuditDir 'headers.txt'
$geoHtml = Join-Path $geoAuditDir 'page.html'
$geoRobots = Join-Path $geoAuditDir 'robots.txt'

# GET 并跟随跳转；保留各跳转响应头和最终正文
curl.exe -sS -L --max-redirs 5 --connect-timeout 10 --max-time 30 `
  -D $geoHeaders -o $geoHtml `
  -w "status=%{http_code} final=%{url_effective} type=%{content_type}\n" $geoUrl
if ($LASTEXITCODE -ne 0) { throw '请求失败；先检查网络、证书或跳转，不分析残缺结果。' }

curl.exe -sS --connect-timeout 10 --max-time 30 `
  -o $geoRobots -w "robots_status=%{http_code}\n" ($geoOrigin + '/robots.txt')
if ($LASTEXITCODE -ne 0) { throw 'robots 请求失败；记录错误后单独排查。' }
Get-Content -LiteralPath $geoHeaders
Get-Content -LiteralPath $geoRobots

# 初筛标签；这不是 HTML 解析器，仍需人工检查完整标签和所属页面
$geoSource = Get-Content -LiteralPath $geoHtml -Raw -Encoding UTF8
[regex]::Matches($geoSource, '(?is)<(?:meta|link)\b[^>]*(?:robots|googlebot|canonical)[^>]*>') |
  ForEach-Object { $_.Value }
# 换成页面里一段独特的真实正文，检查原始响应是否包含它
$geoSource.Contains('适合 4 至 6 人的独立会议室')
```

**怎样读结果：** `status=200` 只表示最终响应成功，还要打开保存的 `page.html` 看它是业务正文、登录框、验证码还是“页面不存在”。Google 明确区分正常页面与返回 200 的错误页；2xx 不保证索引。[HTTP 状态与 soft 404](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes)

若输出的 `final` 换了主机名，例如从裸域跳到 `www`，把 `$geoUrl` 改为该最终地址再检查，确保读的是正确主机的 robots。robots 返回 404 不等于全站禁止抓取；若它跳转或请求出错，应继续核对实际规则，不能把错误页当作 robots 正文。

| 观察结果 | 通常要查哪里 | 修复完成后怎样验收 |
| --- | --- | --- |
| 最终 301 / 302、循环或超过 5 次跳转 | 域名、HTTPS、尾斜杠、语言跳转规则 | 用最终公开 URL 再测；重要链接直接指向规范地址 |
| 401 / 403 或正文是验证码 | 登录中间件、CDN / WAF 规则、地区限制 | 匿名请求能取得公开正文；再查真实机器人请求日志 |
| 404 / 410 | 页面删除、路径大小写、CMS 发布状态 | 该保留的页恢复；确实删除的页保留合适状态，不全部跳首页 |
| 429 / 5xx | 限流、服务故障、上游超时 | 先修稳定性，再谈内容实验 |
| 200 但只有空的 `root` / `app` 容器 | 正文是否依赖 JS / 登录 API / 浏览器本地状态 | 对比渲染后正文；重要公开内容考虑服务端渲染或预渲染 |
| 200 且正文完整 | 继续查索引控制、内容覆盖与实际引用 | 不把成功下载当成已被某个 AI 收录 |

普通请求不能证明某家爬虫能访问。若 CDN 日志显示真实机器人被拦，再按该平台当前官方身份验证方法核对 IP 或其他验证信息；手动把 User-Agent 改成爬虫名字，只能测试字符串规则，不能证明真实爬虫已来访。

#### 第三步：检查三个最容易误配的位置

**1. `robots.txt`。** 找目标机器人或通用组里是否禁用了这个路径。`Disallow: /` 可能是测试站配置误上生产；改之前确认是公开页面。robots 管抓取，不负责替你保护私人数据，也不能单独保证 URL 从搜索结果消失。[robots 官方说明](https://developers.google.com/search/docs/crawling-indexing/robots/intro)

**2. `noindex`。** 同时检查 HTML 的 robots meta 和响应头 `X-Robots-Tag`。下例常来自 CMS 的“阻止搜索引擎”开关或部署环境继承：

```html
<!-- 对打算公开索引的产品页：先确认用途，再移除误加的 noindex -->
<meta name="robots" content="noindex, nofollow">
```

不要把网站所有 `noindex` 都删掉；登录、结账、内部搜索等页面可能本来就不该收录。Google 必须能抓到页面，才有机会读到其中的 `noindex`。[noindex 的实施条件](https://developers.google.com/search/docs/crawling-indexing/block-indexing)

**3. `canonical`。** 独立产品页误指向首页，会发出不一致信号；同一页面的跟踪参数版本通常应指向选定的干净地址。canonical 是规范化信号，不是强制命令。[规范 URL 官方说明](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)

```html
<!-- 本教学页面选择的规范地址；应与站内链接及 sitemap 一致 -->
<link rel="canonical" href="https://example.com/meeting-rooms/small-team">
```

对于 JS 页面，在浏览器检查最终 DOM，核对 `title`、canonical、robots 和正文有无被脚本改写；有 Search Console 权限时，再检查 Google 实时测试呈现的 HTML。原始正文缺失、浏览器正文存在，只能证明渲染依赖；Google 能执行 JS，不等于所有 AI 抓取器都有相同能力。[JavaScript 抓取、渲染与索引](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)

#### 第四步：把一句卖点改成用户能拿来做决定的内容

**改前：** “高端会议室，配置齐全，价格优惠，满足多样化商务需求。”

**改后示范（虚构事实，不能直接挪作真实宣传）：**

> 这间独立会议室适合 4 至 6 人面试或讨论。房间有可连接 HDMI 的显示屏、白板和独立电源；不提供视频会议摄像头。工作日 9:00—18:00 可预约，按小时计费，至少预订 1 小时。需要远程会议时，请自带摄像头并提前测试设备。实时价格和可预约时段在预订页确认。

再补三块证据：**一张本人拍摄的实际房间图、一次真实接屏步骤、公开的取消规则**。照片下方写地点和拍摄日期；关键价格、人数和限制用正文表达，不能只藏在海报里。图片展示事实，不用图库照片冒充该房间。

给页面补上从分类页进入的普通链接，例如 `<a href="/meeting-rooms/small-team">4 至 6 人会议室与设备说明</a>`。不要让发现路径只剩“点击 JS 按钮后才出现的地址”。[可抓取链接与锚文本](https://developers.google.com/search/docs/crawling-indexing/links-crawlable)

#### 第五步：照着这份 7 天清单执行

| 天 | 具体任务 | 当天交付 / 通过标准 |
| --- | --- | --- |
| 1 | 从客户咨询选 10 个问题；品牌题、非品牌题分开；在目标 AI 的联网入口保存当前回答 | 10 题原文、入口、时间、联网状态、引用 URL、业务事实是否正确 |
| 2 | 对目标页及首页运行上述检查；核对 robots、noindex、canonical、渲染 | 响应头和 HTML 文件；每个障碍有负责人与修复位置 |
| 3 | 从合同 / 后台 / 实际产品确认关键事实，补一份内容清单 | 人数、设备、时间、价格口径、限制各有事实来源 |
| 4 | 改一页正文，拍一张真实配图，写清楚如何到达或使用 | 不了解业务的人能回答“适不适合我、下一步怎么做” |
| 5 | 发布；从相关页加链接；更新真实修改过的 sitemap 项 | 公共 URL 可访问；源码、链接、规范地址一致；保留发布差异 |
| 6 | 在已验证的站长工具内检查 URL；有适用功能才提交重新抓取 | 记录“提交成功 / 已抓取 / 已索引”各自状态，不合并 |
| 7 | 复跑题集，检视咨询与预订入口；安排后续每周同条件复测 | 一份技术验收与一份效果观察；仍为零的结果也保留 |

sitemap 提交是帮助发现 URL 的提示，不能规定搜索引擎何时处理。只有内容真的更新才更新相应 `lastmod`。[sitemap 生成与提交](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)

#### 怎样知道这周做对了；没有效果时先查什么

本周先验收可控结果：公开正文可读取、关键事实准确、目标页有入口、CTA 能用。索引、AI 引用和询盘需要继续观察；7 天是执行计划，不是收录或增长时限。

测量表至少分开：**目标页索引状态、题集中的正确品牌提及、官网引用、可识别 AI 引荐会话、完成业务事件**。前后使用相同题集与入口；品牌题容易命中，不能混入非品牌题把平均值抬高。

| 症状 | 下一步 |
| --- | --- |
| 技术正常，始终没被搜到 | 检查发现路径、站长工具状态、内容是否与其他页重复；不要一天提交几十次 |
| AI 引用旧页 | 保存实际旧来源，检查旧页面、重定向与外部资料；先更新源事实，再等待各平台处理 |
| 引用了但说错 | 看错误事实来自哪一页；把条件写进对应句子附近，消除表格与正文冲突 |
| 被提到但没访问 | 检查回答有没有给链接、是否已经满足需求；提及与访问分开报告 |
| 有访问但没有预订 | 检查移动端、目标门店是否匹配、价格是否跳变、登录是否过早；这可能是转化问题 |

#### 先看原文到底测了什么

Graphite 为 Webflow 测试两项改动：添加文章目录、把小标题改成问题。方法段说明 10 个测试 URL 配对 10 个流量与展示相近的对照 URL；观察期写五周，结果段写四周，图示为 2025 年 W33—W37。[原始案例与方法](https://graphite.io/five-percent/case-studies/webflow-llm-signups)

| 原始证据 | 目录实验 | 问句标题实验 |
|---|---|---|
| AI visits 前后均值 | 119 → 127 | 41 → 70 |
| 作者报告的对照校正提升 | 60% | 58% |
| 作者报告的 p 值 | 0.002 | 0.001 |

原文称对实施前后各周取平均后与对照比较；没有公开逐 URL 数据、完整对照计数、精确公式与 AI 来源识别规则。两个实验是否共用同一组页面也不清楚。上述数字不能独立复算，更不能据此承诺相同效果。

#### 打开两张真实页面，看改动落在哪里

| 页面入口 | 今天可以直接检查的结构 | 这一步能确认什么 |
|---|---|---|
| [Landing pages vs. websites](https://webflow.com/blog/landing-pages-vs-websites) | 正文前有链接目录；章节覆盖区别、适用情境、示例 | 能看见具体导航与章节的对应关系 |
| [AI design tools](https://webflow.com/blog/ai-design-tools) | 定义、优势、限制、工具选择等部分采用问句标题 | 能看见标题承接了什么读者问题 |

本项目在核验日读到了这些结构。两页都标注更新于 2025-10-24，晚于案例图示的实验周次，**当前页面只能用于观察结构，不能充当实验当日截图，也不能证明当时只改了这些内容**。前一页的 “When do you need a website?” 与后一页的 “What are the limitations of AI in web design?” 都是可定位的观察点。[页面一](https://webflow.com/blog/landing-pages-vs-websites)、[页面二](https://webflow.com/blog/ai-design-tools)

#### 先把百分比算明白

只根据表中均值计算，目录实验原始变化是 `(127 - 119) / 119 ≈ 6.7%`；问句标题原始变化是 `(70 - 41) / 41 ≈ 70.7%`。这是本项目的算术核对。它们与作者的校正结果不同，不必然矛盾，因为后者还引入了对照组；缺少对照明细时不要硬凑公式。

**下面是本项目独立设计的教学数据，全部为合成数字，与 Webflow 无关。** 用它理解“自身增长”和“相对对照变化”的差别：

| 四周合计 AI 引荐会话 | 修改前 | 修改后 | 自身变化 |
|---|---:|---:|---:|
| 测试组 | 100 | 120 | +20% |
| 对照组 | 100 | 80 | -20% |

本教学例子预先选择“相对变化比”作为描述指标：

```text
相对变化比 - 1 = (测试后 / 测试前) / (对照后 / 对照前) - 1
               = (120 / 100) / (80 / 100) - 1
               = 50%
```

因此同一批数据可以同时得到“测试组原始增长 20%”和“相对对照变化 50%”。这不是 Graphite 公式的还原。也可以报告绝对差分 `(120-100)-(80-100)=40` 次会话，但不要把 40 次写成 40%。基线为零时比值不定义，改报数量，不人为补一个 1 让公式工作。

#### 跟做一个你能解释清楚的目录实验

以下方案由本项目设计，用来练习，不是原案例的内部实验方案。

##### 1. 只选一个假设

本轮假设写成：**“已有长文增加可点击目录后，测试页面获得的 AI 引荐会话，相对同期未改页面是否改善？”**

不要同时重写正文、增加 FAQ、改问句标题和买外链，否则最后无法回答哪项改动与变化有关。原文中的两个技巧应拆成两轮练习。

##### 2. 配对后再分组

有足够数据时，从同一网站选 20 篇既有长文，按主题、页面类型、近四周访问与展示、发布时间配成 10 对。排除活动即将下线、正改版、几乎没有数据的页面。每对用抛硬币或可记录的随机方式指定测试页，另一页作对照；分组一旦写进日志，不因结果不好换页。

**填好的配对记录示例：** `pair-01` 包含“客户访谈准备清单”和“用户访谈记录方法”，同属研究教程、均已上线六个月以上；基线四周 AI 引荐会话分别为 12 和 13，随机分组后前者添加目录，后者保持原样。数字为教学设定，真实项目使用后台导出值。十对只是组织练习的规模，不能自动保证统计功效；样本太小就如实报告探索性结果。

##### 3. 在一个页面上先把动作验收通过

测试页改动清单只有三项：给现有二级标题设置唯一锚点、在引言之后添加对应链接目录、检查每项实际跳到正确位置。**标题文字与正文不改。** 如果原文结构本身不合理，先把它排除，另开内容修改任务。

保存 `before.html`、`after.html`、差异文件和前后截图；点击目录逐项检查实际视口、移动端和键盘操作。记录具体发布时间。修改发布成功，不等于平台已经重新抓取；有可验证日志时另记抓取时间，没有就写未观察到。

##### 4. 在查看结果前固定指标

本轮主指标是“落地到这 20 个 URL 的 AI 引荐会话”，需要记录分析工具、来源过滤、时区、会话口径、测试流量排除规则。另列注册数量与会话转化率，不把它们与引用数量相加。若追踪固定问题的引用结果，另建一张表，不能用人工问答次数冒充网站会话。

基线四周、实施日、后续四周连续记录；将发布日所在的不完整周期单列。平台故障、品牌活动、内容迁移、追踪代码更换都进备注。若数据延迟，等同等成熟度后再比较。

##### 5. 先看每对，再看总计

如果总增长完全来自一篇热点文章，不能写成“所有目录都有效”。并列展示每对的前后数、组总计、周走势与异常；没有增长和下降的页面同样保留。不要对四个聚合周值随意套一次 t 检验，就声称获得可靠因果结论；页级差异、重复观测和共同趋势需要在分析设计中处理。

**合成数据的一份正确结论示范：** “四周窗口中，测试组会话 100→120，对照组 100→80；按预先定义的相对变化比，描述性差异为 +50%。目前未提供样本级不确定性估计，也无法排除同期差异，下一轮保留配对并增加观测。结论是值得继续检验目录改动，不是已证明目录普遍提升 AI 排名。”

**毕业要求：** 另一位读者拿到你的分组表、URL 清单、页面差异、原始导出、指标定义和计算式，能得到相同数值，并知道哪些页面没改善。只发一张“提升 60%”图片，尚未完成这项练习。

</details>

<a id="playbook-miniprogram"></a>

### 3. 微信小程序如何做 GEO

**要解决的问题：** 服务都在小程序里，外部 AI 不知道卖什么，用户看到介绍也不知道怎么进入。

**适用对象：** 预约、零售、工具、教育等微信小程序；其他平台小程序需另查各自规则。

**先准备：** 公开产品事实、可维护的介绍页面、小程序已发布路径和实际转化事件。

**本周交付：** 一份公开产品说明、一组内容到小程序的落地映射、一份端到端测试记录。

**从这里动手：** 把“让公众读到服务事实”和“进入小程序完成任务”分别打通。

<details>
<summary>展开小程序教程：公开内容 → 路径映射 → 入口实测 → 归因</summary>

![小程序的公开资料发现链与实际转化链需要分别验证](assets/mini-program-path.png)

#### 第一步：先确认你要让哪一种系统发现什么

| 层 | 要检查的对象 | 能推出什么 / 不能推出什么 |
| --- | --- | --- |
| 微信内发现 | 实际微信搜索结果、小程序当前后台配置 | 微信里搜到，不等于 ChatGPT 或其他 AI 能直接读取小程序页 |
| 公开信息 | 官网、公开帮助、商品 / 服务说明、公众号文章 | 能在浏览器读到，不等于已经进入任何指定 AI 的检索集合 |
| AI 回答 | 目标 AI 本次实际引用的来源 URL | AI 引用了公众号文章，只能证明这一轮使用了这篇文章 |
| 小程序使用 | 入口、目标路径、登录、预约 / 购买 / 激活 | 成功打开小程序，不代表完成了业务目标 |

**本轮能核实的官方材料：** 微信官方 [miniprogram-demo 的 sitemap 示例](https://github.com/wechat-miniprogram/miniprogram-demo/blob/master/sitemap.json)包含 `rules`、`action` 和 `page` 配置；官方 [API 类型定义](https://github.com/wechat-miniprogram/api-typings/blob/master/types/wx/lib.wx.app.d.ts)列出了打开路径、query、场景值，以及 URL Link 入口。这些材料不证明公众 AI 可以读取全部小程序内容，也不证明元宝直接收录了你的小程序。

**实施前需在自己的后台复核：** [sitemap 文档](https://developers.weixin.qq.com/miniprogram/dev/framework/sitemap.html)、[URL Link 文档](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/url-link.html)本轮工具未能取得正文；账号资格、跳转条件、配额及最新限制以实际后台和官方页面为准。下文不假定所有账号都能使用同一种外部跳转方式。

#### 第二步：没有官网、已有官网、只有公众号，分别怎么做

| 现状 | 最小可执行方案 | 验证方法 |
| --- | --- | --- |
| 有官网 | 增加一页公开产品 / 服务详情；在该页完成事实解释，再引导到小程序 | 用上条网站路线检查响应和正文；实际点击小程序入口 |
| 只有小程序 | 建一页自己能持续维护的公开说明；内容不多可用单页，先不建设整套内容站 | 未登录的外部浏览器能读懂产品、条件、费用口径和使用步骤 |
| 只有公众号 | 发布有文字正文的使用说明，并逐篇测试分享链接在微信外的可访问性 | 无痕窗口、手机非微信浏览器各打开一次；记录正文 / 验证码 / 登录 / 错误 |
| 商品或服务都需要登录 | 公开通用说明和适用条件；账户记录与实时私人数据仍留在登录后 | 陌生人能判断是否适合，但读不到任何客户个人资料 |

公众号文章若在某个环境出现验证或打不开，记录该条件，不把它称为“全网可抓取”。若目标 AI 实际引用了文章，打开引用链接核对完整内容。只有官方产品说明提到“公众号资源”，仍不足以确认某篇文章已被纳入。

#### 第三步：用一个具体例子把公开页面和小程序页面接上

以下是**虚构的“海湾自习室”预约小程序**。目标问题是“附近有没有周末可用、允许带电脑的安静自习室”。表中路径和名称是教学设计；真实项目换成真实门店、政策与已发布路径。

| 用户实际要问 | 公开页需要回答的事实 | 小程序承接位置 | 谁维护 |
| --- | --- | --- | --- |
| 在哪里，周末开不开 | 门店名称、地址、交通文字、周末营业时段、拍摄日期明确的门店图 | `pages/store/detail?id=harbor-01` | 门店运营 |
| 可以带电脑吗 | 允许的座位区、插座、通话规则；不要只放一个“设施齐全”图标 | 同店的座位类型说明 | 店长 |
| 多少钱，能退吗 | 按小时 / 天计费方式、优惠适用范围、取消条件；实时空位在小程序确认 | `pages/booking/create?store=harbor-01` | 价格 / 订单负责人 |
| 如何预约 | 选门店 → 选日期座位 → 确认规则 → 支付；每步真实截图 | 对应门店或预约页，避免全部落到小程序首页 | 产品负责人 |

**改前：** “环境优美、设施齐全、学习首选。扫码了解更多。”

**改后示范（虚构）：**

> 海湾自习室的电脑区允许使用笔记本，座位配有电源。静音区不适合线上会议，通话需离开座位区。预约时先选择“电脑区”，再查看具体日期的空位和价格。周末营业时间、门店地址和取消规则见本页；点击“查看该店空位”进入对应门店，不需要重新搜索名称。

配三张真正有教学作用的图片：**门店实际入口、电脑区座位、小程序预约路径截图**。图注解释拍摄 / 截图时间及对应步骤；正文同时写出关键信息。二维码旁保留小程序准确名称与必要的文字步骤，手机用户可能无法方便地扫描当前屏幕。

#### 第四步：测试入口，不把“生成一个链接”当作完成

1. 由后台或开发者使用账号当前获准的方式生成目标入口。URL Link、二维码、微信内卡片是不同入口，分别测试；没有权限的入口不要强行照抄别人的方案。
2. 为公开页到小程序的跳转设置自己的来源标记，例如 `source=public_guide`、`campaign=studyroom_202610`；只用不含个人信息的业务标记，先确认该入口允许携带参数。
3. 小程序接收路径与 query 后，验证门店 ID 存在、页已发布、参数没有丢失。不要因为参数异常直接落回首页而不记录错误。
4. 至少测四种条件：手机微信内、手机微信外、桌面浏览器、已安装但未登录。记录设备与微信版本；不支持的条件提供可理解的替代路径。
5. 从“查看空位”一直测到确认页；测试账户用于测试，避免为了验证而产生真实扣款。门店、日期和价格必须贯穿一致。

官方类型定义支持记录进入时的 `path`、`query`、`scene`；这些字段本身没有告诉你“这是某个 AI 带来的访问”。`scene` 是微信入口场景，不能直接改名为 AI 来源。[微信官方打开参数定义](https://github.com/wechat-miniprogram/api-typings/blob/master/types/wx/lib.wx.app.d.ts)

#### 第五步：一周内完成一个公开内容到预约的闭环

| 天 | 做什么 | 交付物 |
| --- | --- | --- |
| 1 | 导出或人工整理 10 条脱敏客服原话，选一个门店与一个预约任务 | 问题表：问法、缺失事实、谁能确认 |
| 2 | 核对地址、营业时间、座位规则和取消规则；拍实际照片 | 有负责人和更新时间的事实卡 |
| 3 | 发布一份可读的公开说明，或改好现有说明 | 一个公开 URL；正文可读性测试记录 |
| 4 | 生成获准的小程序入口，写好目标路径与来源映射 | 一张 URL / 二维码 → 页面路径 → 业务事件表 |
| 5 | 用四种条件完成入口测试，修掉失效和落错门店的问题 | 屏幕截图、测试时间、是否到达正确页面 |
| 6 | 在目标 AI 联网入口跑固定问题，保存真实引用 | 回答与来源存档；没引用也记录 |
| 7 | 检查公开页阅读、入口点击、小程序到达和完成预约 | 漏斗报告；下一周只优先修最大掉点 |

#### 验收与排错：曝光问题和转化问题分别处理

| 症状 | 怎么定位 | 下一步 |
| --- | --- | --- |
| AI 完全不知道小程序 | 查有没有可公开读取的产品事实，搜索结果与 AI 引用究竟是什么 | 补真实公开说明与相关资料；不承诺提交一次即可收录 |
| AI 能回答但没给入口 | 看被引用页是否有明确名称、适用入口和操作步骤 | 给该页补“怎样使用”，别只重复品牌词 |
| 外部文章可读，点击却打不开 | 对比账号权限、入口有效性、设备与环境 | 按当前官方条件调整入口，保留替代说明 |
| 打开成功但进入首页 | 检查目标路径、query、发布版本和参数处理 | 恢复到对应门店 / 商品；记录回退原因 |
| 小程序到达很多，预约很少 | 看价格差异、满位、手机号授权时机、支付与取消规则 | 修转化流程；不能直接推断 GEO 无效 |

分别报告：**AI 回答中的正确提及 / 引用、公开页访问、跳转按钮点击、小程序到达、去重完成订单**。保留下游业务口径与时间窗口。AI 可能不给 referrer，二维码也可能被转发；来源参数只能识别这条入口，不能证明每次访问来自 AI。无法确定的来源写“未知”，可另用自愿回答的“从哪里了解到我们”辅助判断。

</details>

<a id="playbook-product"></a>

### 4. 独立产品如何做 GEO

**要解决的问题：** 产品做出来了，AI 不理解它适合谁，只知道大品牌，或仍在描述旧版本。

**适用对象：** 独立开发者的桌面软件、移动 App、SaaS、浏览器插件。

**先准备：** 能实际使用的产品、明确的版本 / 价格 / 限制、一个公开信息入口。

**本周交付：** 一套产品事实、关键决策页面、真实截图和一次完整使用教程。

**从这里动手：** 选定一个目标任务，让陌生人从“是否适合”一路找到“怎样成功使用”。

<details>
<summary>展开产品教程：产品类型判断 → 七类页面 → 写完示范 → 7 天交付</summary>

#### 第一步：产品形态不同，先补的信息也不同

| 产品类型 | 第一批必须讲清楚的事实 | 转化与验收 |
| --- | --- | --- |
| 桌面软件 | 支持的系统 / 芯片、最低版本、离线范围、安装与卸载、数据位置、授权方式 | 成功安装 → 完成第一个真实任务；下载次数只是中间事件 |
| 移动 App | iOS / Android 支持、地区、账户要求、订阅与内购、权限用途、数据同步 | 商店访问 → 安装 → 关键任务；尊重平台归因限制 |
| SaaS | 使用对象、工作流、计费单位、套餐限制、集成、导出、服务地区与支持 | 注册 → 激活 → 有意义的持续使用；不能把所有注册算有效用户 |
| 浏览器插件 | 支持浏览器、作用页面、请求权限及原因、数据处理、与官网的对应关系 | 商店访问 → 安装 → 成功触发核心功能；排查站点与版本兼容 |

App 的商店页应展示真实界面与功能；插件也应使用准确标题、摘要、说明和截图，避免堆关键词。这是公开产品信息与分发的基本功，不是商店“已经证实可提升 AI 推荐”的保证。[Apple 产品页指南](https://developer.apple.com/app-store/product-page/) · [Chrome Web Store 列表指南](https://developer.chrome.com/docs/webstore/best-listing)

#### 第二步：先写产品事实表，别让七个页面讲七个版本

下面贯穿一个**虚构产品“句记 JotLocal”**：帮助研究者把本地访谈录音整理成带时间戳的文字。全部功能、版本和价格都是教学设定，**不是实际产品，也不是增长案例**。

| 字段 | 本例填好值 | 真实项目在哪里核对 |
| --- | --- | --- |
| 当前形态 | Windows 桌面软件，v1.2；不提供手机版 | 实际安装包、发布记录 |
| 目标任务 | 导入已有中文访谈音频，修改转写并导出 TXT / SRT | 从头完成一次操作 |
| 系统条件 | Windows 11 x64；首次下载模型需要网络 | 安装测试与产品配置 |
| 离线边界 | 模型就绪后可在本机转写；更新检查仍可能访问网络 | 按功能做网络与数据流检查 |
| 明确不支持 | 实时会议机器人、多人云协作；不保证自动分清所有说话人 | 当前版本功能与缺陷列表 |
| 计费示例 | 个人版 ¥129，一次购买当前大版本；不承诺未来大版本免费 | 实际授权条款、收银台、退款政策 |
| 证据 | 真实界面截图、可公开的测试音频、处理步骤、已知错误记录 | 原始文件与测试环境 |

事实表先被开发者核对，再分发到官网、帮助、商店和外部目录。新版本发布时反查这张表；不要让首页写支持 Mac，安装页却只有 Windows。

#### 第三步：围绕同一个用户任务，做出七类信息

这是信息任务清单，**不是要求新产品上线七个空壳页面**。内容少时先合并成一个清楚的页面；有足够独立问题和细节时再拆分，拆分后互相链接。

| 页面 / 区块 | 本例具体写什么 | 应放的证据 | 用户下一步 |
| --- | --- | --- | --- |
| `/` 首页 | “Windows 本地访谈转写工具”；谁适合、输入输出、三步操作、不支持什么 | 一张真实编辑器截图；可公开的示例输出 | 看教程 / 检查系统条件 |
| `/docs/first-transcript` 文档 | 首次下载模型 → 导入 WAV / MP3 → 校对 → 导出；每一步失败提示 | 每步真实截图、示例音频、预期文件 | 先试一次再决定 |
| `/pricing` 价格 | 币种、税费说明、一次性还是订阅、设备数、升级范围、退款入口 | 与实际结账及授权条款一致的事实 | 选版本并确认总价 |
| `/alternatives` 选择指南 | 本地桌面转写、云转写、人工整理各自适用条件；不把所有竞品写成更差 | 当前一手功能 / 价格来源，注明核对日期 | 根据保密、协作、设备做选择 |
| `/use-cases/research-interviews` 场景 | 一段访谈如何保留时间戳、校对术语、导出给研究笔记 | 脱敏输入、步骤、输出、需人工检查的错字 | 完成自己的第一段访谈 |
| `/changelog` 更新日志 | v1.2 改了哪项导出行为、旧用户如何升级、已知问题 | 对应版本、发布日期、实际发布记录 | 确认旧教程是否仍适用 |
| 商店 / 外部目录条目 | 准确名称、开发者、官网、系统、定位、真实截图；按平台字段填写 | 真实可访问产品页与下载 / 商店入口 | 核对来源并进入官方页面 |

对比页若涉及具体竞争产品，逐项链接对方官方文档，未核实的项目填“未确认”。不要发布“十大最佳工具”再把自己的产品无证据排第一。目录条目只提交到适用且愿意维护的平台，不能购买或伪造用户评价来补所谓信任信号。

#### 第四步：给三段能直接模仿结构的写作示范

**首页改前：** “革命性 AI 生产力工具，让工作效率提升 10 倍。”

**首页改后（本例设定）：**

> 句记 JotLocal 是面向 Windows 用户的本地访谈转写工具。导入 WAV 或 MP3 后，可在文字编辑器中校对识别结果并导出带时间戳的 SRT。首次使用需要下载模型；模型就绪后，本地转写不要求上传录音。它适合已经录好的访谈，不适合需要实时会议机器人或多人在线协作的团队。查看系统要求与第一份转写教程后，再决定是否安装。

**教程开头与步骤（本例设定）：**

> 本教程把一段自己有权处理的访谈录音转成 SRT。开始前确认 Windows 11 x64、已完成模型下载，并保存原录音备份。点击“导入”选择文件；转写完成后先核对人名、专业词和每一段时间戳；点击“导出 → SRT”。用实际目标播放器加载字幕，检查第一段、一次长停顿和最后一段是否同步。识别结果仍需人工校对，不能因为导出成功就视为文本准确。

**选择指南中的一行（本例设定）：**

| 真实条件 | 本地桌面工具 | 云协作工具 | 需要读者进一步确认什么 |
| --- | --- | --- | --- |
| 多人需同时校对一份转写 | 本例句记 v1.2 不支持 | 查目标服务的共享、权限和共同编辑文档 | 团队席位费、数据处理条件、导出方式 |

这一行没有给虚构“准确率”，也没有捏造竞争者功能。真正做对比时，把“云协作工具”替换成核对过的具体产品与版本，并附其一手来源。

#### 第五步：拍什么图、放在哪里

1. **首页一张结果图：** 展示时间戳、文本和导出入口；截取实际产品，不用概念海报代替界面。
2. **教程三张过程图：** 导入、校对、导出；在图上标出这一节要点，正文仍保留完整步骤。
3. **场景一组输入输出：** 使用有授权、已脱敏的短样本；标注哪些地方仍需人工修正。
4. **兼容性一张表：** 系统、版本、支持状态用文字表格维护，不做只有像素内容的参数长图。

演示里出现的客户名称、文件路径或录音内容先脱敏。真实用户评价须有实际来源与适用的展示许可；教程所用虚构样例必须像本节一样明显标明。

#### 第六步：独立开发者的 7 天最小计划

| 天 | 工作 | 明确交付 |
| --- | --- | --- |
| 1 | 从支持问题、访谈和自己的完整使用测试提取购买阻碍 | 10 个真实问题，按适用性 / 兼容 / 费用 / 使用 / 替代分类 |
| 2 | 填产品事实表，核对当前版本 | 一份开发者确认过的事实清单；未知项不对外宣称 |
| 3 | 改首页与价格区块，补实际界面图 | 一眼能回答“做什么、给谁、要什么系统、多少钱” |
| 4 | 写并亲自走完第一次使用教程 | 新用户照着步骤能得到一个正确格式的输出文件 |
| 5 | 写一个场景教程和必要的选择比较；整理更新日志 | 页面中的关键结论有原始证据或可重做步骤 |
| 6 | 更新真实存在的商店 / 目录资料；检查官网发现与访问 | 名称、系统、版本、描述无冲突；重要页有普通链接 |
| 7 | 用固定题集复测，查看新用户在哪一步失败 | 原始回答与引用记录、一份激活漏斗、下一次优先改动 |

#### 验收：用三类题测，不只问 AI “你知道句记吗”

| 类别 | 本例测试问题 | 观察内容 |
| --- | --- | --- |
| 非品牌任务题 | “Windows 上如何把已有访谈录音转成带时间戳的文字，尽量在本机处理？” | 有无提及产品；是否给出适用条件与引用；不预设必须推荐自己 |
| 品牌事实题 | “句记需要联网吗，支持 Mac 吗？” | 首次下载与本地处理是否区分；有没有编造 Mac 版 |
| 决策比较题 | “一个人做访谈整理和 5 人共同校对，应该选什么形态的工具？” | 是否按实际需求选择；不适合时是否正确说明限制 |

上表只是为虚构产品编写题目的示范，不能直接拿“句记”去测平台。实际执行前，将产品、事实和题目全部替换为你自己的真实项目，再按同题同入口保存基线、复测与实际引用页。真实新产品未出现也保留记录；品牌题答对，只说明特定事实被正确表达。把**品牌事实正确率、非品牌题提及 / 引用、来源明确的访问、完成首次核心任务的用户数**分开报告。

**常见失败：** AI 引用旧商店描述时，先更新那条源资料；总被当作同名产品时，统一开发者、产品名、官网与版本；下载安装很多但没有输出时，先修安装、模型下载或首次使用教程；没人需要所写场景时，回到用户问题，而不是继续铺同义关键词页。

### 5. 本地生活商家如何做 GEO

**要解决的问题：** 顾客问“附近哪家适合我”时，AI 能否找到你的门店，准确说明营业时间、价格、服务条件，并让顾客顺利打电话、导航或预约。

**适合谁：** 餐饮、咖啡、美容美发、健身、酒店民宿、维修家政等有真实门店或明确服务区域的商家；不要求先建独立网站。

**完成后交付：** 一张门店事实卡、一份跨平台纠错记录、6 条能回答顾客问题的内容、固定中文问题的观察表，以及电话／导航／预约与到店记录。

<details>
<summary>展开实操：从经营资料到地图、内容、AI 推荐与到店，用一家社区咖啡店走完整条路线</summary>

#### 先选对自己的成交问题

| 行业 | 顾客真正要确认的事 | 本轮优先补充的证据 |
|---|---|---|
| 餐饮／咖啡 | 预算、菜品、包间／座位、是否预约、停车、特殊时段 | 当前菜单、套餐条件、入口与座位实拍、营业与接单时间 |
| 美容美发 | 谁提供服务、项目包含什么、耗时、预约、额外收费 | 服务清单、人员实际作品、价目与预约说明；不延伸医疗承诺 |
| 健身 | 场地器械、课程时段、预约、单次／次卡范围 | 当前课表、场地实拍、课程与使用条件；不许诺健康结果 |
| 酒店民宿 | 具体房型、入住退房时间、停车、床型、设施、预订条件 | 对应房型实拍、日期对应价格、设施与取消条件 |
| 维修家政 | 是否覆盖这个区域、能否接这个任务、何时上门、怎样报价 | 服务区域、受理／不受理项目、上门费与配件费用说明 |

这几类商家可以走同一条资料与观测流程，但不能共用一份“附近推荐”题集。例如，酒店价格必须带日期，维修报价要带故障和上门地点，咖啡店则先回答座位与时段。

#### 第 1 步：用实际经营凭据建立事实卡

找店长或经营负责人确认资料，依据包括招牌、经营资料、当前菜单／价目、实际排班、设备与场地照片、预约记录。证件用于核实和平台审核；公开内容只放顾客需要的营业事实，不把证件号、个人手机号等内部材料复制进文章。

下面是**原创教学设定**：“巷里咖啡”是虚构门店；没有真实地址、联系方式或排名，不应拿它去注册平台。

```yaml
门店名称: 巷里咖啡（教学虚构）
演练位置: 中国某市 A 区的社区底商；未设真实街道和门牌
经营类型: 到店咖啡与简餐，不提供包场
常规营业: 周二至周日 09:00–18:00；周一休息
最后接单: 饮品 17:30；简餐 14:00
价格样例: 美式 22 元；拿铁 28 元；鸡肉三明治 32 元
座位情况: 室内 12 席；无包间；仅靠墙 4 席设插座
预约: 仅接受工作日 2–4 人座位预约；需店员确认，周末不预留
停车: 无自有停车位；不承诺附近一定有空位
使用边界: 不接受视频会议或扩音；不提供儿童游乐区
宠物情况: 本教学设定不接待宠物入内
联系电话: 教学示例不设置；真实项目填写门店可接通电话
信息确认: 店长依据当期菜单与排班确认，2026-10-14
```

不要把“有 4 个插座座位”写成“最适合所有人办公”，也不要把“接受预约”写成“随时有位”。每个卖点都要能回到事实卡中的条件。

#### 第 2 步：先修正顾客能看到的公开门店资料

把美团／大众点评、高德地图、百度地图、腾讯地图、已有抖音门店或经营账号列成检查表。先搜索门店名称与地址，确认是自己的那家店；名称相似的分店、搬迁旧址、重复地点分别处理，不批量新建相同门店。

| 渠道 | 本轮能核查的内容 | 官方依据与读取边界 |
|---|---|---|
| 美团／大众点评 | 门店信息、头图／相册、套餐与服务说明 | [到店餐饮信息发布规范](https://rules-center.meituan.com/m/detail/guize/86?activeRule=1) 明确覆盖上述信息；已读正文，后台按钮未核验 |
| 高德地图 | 地点是否存在、位置是否准确、可控制的门店信息 | [官方标注中心](https://g.amap.com/center?showLogin=true) 的公开索引说明地点标注与管理；登录后台未核验 |
| 百度地图 | 名称、地址、坐标、电话、营业状态与时间、门店图片 | [官方商户中心](https://didian.baidu.com/?bussiness_trigger=1) 的公开索引列出这些管理能力；动态页面未完整直接读取 |
| 腾讯地图 | 先核对搜索到的地点、入口位置和联系方式 | [腾讯位置服务](https://lbs.qq.com/) 当前主页可读；本轮未读到可用的现行商户后台说明，不提供臆测按钮路径 |
| 抖音 | 现有经营身份、公开门店或账号信息、内容与团购条件 | [官方商家中心](https://business.douyin.com/site/brand) 公开索引区分商家中心、来客、抖店与企业号；本轮未核验登录后字段 |

这张表说明的是**商家应核对哪些公开资料**，不是“某中文 AI 优先抓哪个平台”的名单。各渠道是否被某次回答采用，要看该次实际来源。

填好的纠错记录示例：`百度地图／常规营业／旧值每天 09:00–20:00／正确值周二至周日 09:00–18:00／依据店长排班确认／状态已提交待审核`。待审核不等于前台已更新；审核后再从顾客视角检查一次，并走到真实入口核对导航落点。

#### 第 3 步：把 FAQ、价目和预约说明写到顾客决策的位置

先回答来电与私信中最常见的问题，再选平台实际支持的字段、门店介绍、商品说明或公开笔记承载。不要把所有内容挤到店名里。每条价格写清对应产品／服务、份量或时长、适用时段、是否含额外项目；活动与日常价格分开。

**教学示例的三条完整回答：**

- **周一上午可以去办公吗？** 周一休息。其他营业日为 09:00–18:00，室内有 12 席，其中靠墙 4 席有插座；座位不保证随到随有，也不接受视频会议或扩音。
- **两个人喝咖啡加简餐，大约多少钱？** 按本例当期单品价，两杯拿铁加两份鸡肉三明治合计 120 元；简餐最后接单为 14:00。这个组合不是团购套餐，其他选择按实际菜单计算。
- **周末能预约 8 个人一起聚会吗？** 本店周末不预留座位，也不提供包间或包场；目前只接受工作日 2–4 人预约，并以店员确认为准。

验收不是数 FAQ 条数，而是请没参加整理的人模拟打电话：他能否知道今天能不能来、预计点单费用、是否还需确认，以及怎样完成预约。

#### 第 4 步：用 6 条有证据的公开内容覆盖具体场景

围绕同一事实卡制作：① 门口到入店的路线实拍；② 带日期的完整菜单；③ 座位与插座分布；④ 工作日预约说明；⑤ 简餐接单截止时间；⑥ 不适合多人聚会等边界说明。图片配准确图注，视频加必要字幕；公开发布在你已经营且适合承载这些内容的渠道。

例如标题写“巷里咖啡工作日下午座位说明：12 席、4 个插座位、周一休息”，正文用实拍和预约条件支撑；不要改写成“本市排名第一的办公咖啡馆”。没有真实评价不编评价，没有榜单资格不编榜单。

这六条是本项目教学内容任务，不代表发布满六条就会被 AI 推荐。每次修改留下发布日期和来源 URL，过期菜单与活动及时更正。

#### 第 5 步：在目标中文 AI 上重复观察，而非只问一次店名

选你的顾客实际使用的两个入口，例如豆包与一个其他中文 AI；分别记录可见产品／模式、是否联网、测试时间、地区设定与新会话。先保存修改前基线，再在资料确实更新后按同样安排复测。以下是**问题框架与教学问句**。不得拿虚构的“巷里咖啡”和 A 区测试平台自然可见性；真实项目先全部换成真实门店、地区、经营事实和顾客原话，再运行。

| 问题类型 | 教学问句 | 判定重点 |
|---|---|---|
| 非品牌发现 | A 区工作日下午，有插座、适合两个人安静坐一小时的咖啡店有哪些？ | 是否推荐合适门店，是否说明座位不保证 |
| 条件比较 | A 区两个人各喝一杯咖啡、吃一份简餐，120 元左右有哪些选择？ | 预算是否对应具体组合与当期菜单 |
| 即时事实 | 巷里咖啡今天下午四点还能点三明治吗？ | 按教学事实应不能；记录实际测试日期 |
| 品牌核验 | 巷里咖啡周一营业吗？可以预约周末八人聚会吗？ | 两个答案都应否定，不能凭品牌提及算成功 |
| 不适合场景 | 我需要包间开视频会，还要带宠物，巷里咖啡合适吗？ | 正确排除也是事实准确，不应硬求推荐 |

操作量示例：固定 10 题 × 2 个入口 × 每轮 2 次 = 40 个计划样本，连续做基线、更新后一周、再下一周三轮。每题单独开新会话，不在同一会话反复要求“再推荐我”；技术失败单记，不当作未推荐。小样本用于找错误，不冒充城市总体市场份额。

一条填好的教学记录：`Q04／入口 A／新会话／品牌已提及／周一时间说错／来源指向旧菜单／分类=事实错误／动作=检查旧菜单发布入口并更正`。未显示来源时记录“来源未显示”，不能猜它读了美团或小红书。

#### 第 6 步：接上电话、导航、预约完成与到店

| 层级 | 记录什么 | 不能替代什么 |
|---|---|---|
| AI 观察 | 有效回答数、门店提及数、关键信息正确数、可核验来源 | 提及不等于顾客看过，更不等于到店 |
| 行动 | 平台实际提供的电话点击、导航发起、预约发起；保留渠道与日期 | 点击不等于接通，导航发起不等于抵达 |
| 完成 | 接通且需求匹配的咨询、门店确认预约、实际到店／核销 | 不同渠道同一订单要去重 |

预约时可选问一句“最初从哪里知道我们”，把顾客自述与平台可见来源分列；不能把所有新增订单都归给 GEO。若某平台不提供导航或电话统计，就记“不可得”，不补造数字。用同星期几、相近营业条件比较，并记录节假日、优惠活动、天气或临时闭店等变化。

**合格交付示例：** “本轮修正 3 处营业时间、补齐 6 条公开说明；40 个计划样本中 2 个技术失败、38 个有效回答，其中 5 个仍引用旧时段。另有 3 位预约顾客自述从 AI 得知门店，已完成到店 2 位。尚不能证明内容修改导致新增到店。”数字仅为报告写法演示，不是真实成绩。

#### 资源与海外支线

- **国内先读：** [美团到店餐饮信息发布规范](https://rules-center.meituan.com/m/detail/guize/86?activeRule=1)、[百度地图商户中心](https://didian.baidu.com/?bussiness_trigger=1)、[高德标注中心](https://g.amap.com/center?showLogin=true)、[抖音商家中心](https://business.douyin.com/site/brand)。本轮核验日期：2026-10-14；读取与后台边界见上表。
- **腾讯资料：** [腾讯位置服务](https://lbs.qq.com/) 用于确认地图与地点服务入口；商户当前认领／纠错步骤需在其现行官方入口核实，不沿用多年前教程的按钮顺序。
- **海外门店：** 再走 [Google Business Profile 本地结果指南](https://support.google.com/business/answer/7091?hl=en) 与[业务表示规范](https://support.google.com/business/answer/3038177?hl=en)，按当地门店资格与资料要求执行；不把该平台的本地结果规则直接搬给中文 AI。

</details>

### 6. 电商、B2B 服务、创作者与多语言

载体之外，还要处理行业事实。选一个最接近的场景展开：每节都有一份填好的教学示例、具体动作和验收方法。

<a id="playbook-ecommerce"></a>

<details>
<summary>电商：一个 SKU 的价格、变体、库存如何对齐？</summary>

**适用情形：** 用户会问“哪个规格适合我”“现在能不能买”“能否送到这里”，而你的商品信息散落在商品页、商品数据源、结算页和平台店铺中。先选 3—10 个实际 SKU，不从写一百篇选购文章开始。

#### 具体动作

1. **把变体拆开。** 一种颜色、容量或组合包装对应哪个 SKU，逐项列清；记录它实际选中后的 URL、图片、价格与库存，不拿默认款数据代表全部款式。

2. **一次核对四处。** 在同一检查时刻比较商品页、商品数据源、页面结构化数据和结算页。Google Merchant Center 明确要求价格和可用性与落地页等信息一致；错误数据可能影响商品展示资格。[商品数据规范](https://support.google.com/merchants/answer/7052112?hl=en)

3. **把购买条件写成可回答的问题。** 针对真实询盘补充容量、包装内含物、适配条件、配送区域、退货条件；每条都指向制造商资料或店铺真实政策。没有实测就不写“保温 12 小时”，没有分配 GTIN 就不编一个。

4. **留一次完整购买核对记录。** 选择具体变体进入结算前一步，保存价格、币种、库存和运费说明的截图。将“页面能看见”“数据已提交”“平台已处理”“问答已正确引用”分别记录。

#### 填好的教学示例：同款笔记本，绿色已售罄

以下品牌、SKU、价格和库存均为**原创教学设定**，不是真实商家的结果，也不是可直接上传的完整商品 feed。

| 核对字段 | 米白款 | 墨绿款 |
|---|---|---|
| 产品 | 岸线 A5 点阵笔记本，160 页 | 同款不同颜色 |
| SKU / 系列 | NOTE-A5-IV / NOTE-A5 | NOTE-A5-GR / NOTE-A5 |
| 页面选中价格 | 12.00 USD | 12.00 USD |
| 页面库存 | 有货 | 售罄 |
| 数据源库存 | `in_stock` | 错写为 `in_stock` |
| 结算检查 | 可加入购物车 | 无法下单 |
| 本轮处理 | 保留 | 数据源改为 `out_of_stock`；同步检查标记 |

可复制到表格中的一行修复日志：

```csv
checked_at,sku,field,page_value,feed_value,decision,owner,recheck
2026-10-14T10:00:00+08:00,NOTE-A5-GR,availability,out_of_stock,in_stock,修正数据源并重新处理,商品运营,处理完成后核对平台状态
```

改稿后的问答可以具体到：

> **墨绿款现在可以下单吗？** 当前售罄；米白款仍可下单。两款均为 A5、160 页点阵内页。补货时间尚未确认，因此没有给出到货承诺。

练习重点是准确表达库存差别，不是把“售罄”包装成稀缺营销。

#### 验收

- 两个变体的价格、币种与库存各自一致；修复日志能指向具体字段和复查时间。
- 用“12 美元以内、绿色、现在可下单”提问时，正确答案应排除墨绿款；没有推荐该款不能被算成失败。
- 用“点阵 A5 笔记本有哪些颜色”提问时，检查回答是否区分存在的款式与当前可售款式。
- 商品数据提交成功只算技术产物；AI 是否正确描述、是否带来购买，另保留观测记录。

#### 一手资源

- [Google Merchant Center：商品数据规范](https://support.google.com/merchants/answer/7052112?hl=en) — 对照价格、库存、变体和标识符字段，适用范围是该商品平台。
- [Google：商家商品结构化数据](https://developers.google.com/search/docs/appearance/structured-data/merchant-listing) — 检查商品和 Offer 的实现；合规标记不保证展示，也不是 AI 推荐承诺。

</details>

<a id="playbook-b2b"></a>

<details>
<summary>B2B 服务：没有增长数字，如何用交付证据帮助采购？</summary>

**适用情形：** 企业内容制作、设计、翻译、研究、培训等服务。客户不是找一个功能按钮，而是在比较人、流程、交付物、责任边界和项目风险。

#### 具体动作

1. **从最近十条真实询盘中抽问题。** 删除个人信息，保留原话；按“是否适合、能交什么、客户需提供什么、如何验收”四组整理。不要全部写成包含自己品牌名的题。

2. **为一项服务制作交付卡。** 写明确产物、数量、格式、修改轮次、客户依赖与不包含项；流程承诺和结果承诺分开。比如能承诺交付四集音频，不能因此承诺四倍销售线索。

3. **展示能公开的工作证据。** 将获准披露的简报、初稿、审查批注、最终交付组成同一个案例；说明自己负责哪一部分。Google 的内容指南建议交代创作者及制作过程，不能用虚构专家或资历代替证据。[内容可靠性指南](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)

4. **统一团队身份。** 核对官网、可控制的职业资料、行业目录中的名称和身份；公开案例中的组织及作者应能对应。若使用 Organization 标记，`sameAs` 应指向该组织的真实相关资料，不填竞品或随便一篇报道。[组织文档](https://developers.google.com/search/docs/appearance/structured-data/organization)

#### 填好的教学示例：企业访谈播客制作

下面是**原创虚构服务包**，不是真实供应商报价或履历。

| 采购字段 | 已填写的服务范围 |
|---|---|
| 适合谁 | 已有主持人与嘉宾、能自行录音的 B2B 营销团队 |
| 每批输入 | 4 份分轨录音，每份不超过 60 分钟；节目简报、术语表 |
| 每批交付 | 4 集 20—30 分钟音频、校订逐字稿、节目摘要、章节时间戳 |
| 工作顺序 | 接收素材 → 确认剪辑方向 → 首稿 → 客户合并反馈 → 终稿 |
| 修改范围 | 每集 2 轮合并反馈；重录与改变节目方向另评估 |
| 周期起点 | 素材齐备且剪辑方向确认后开始计时 |
| 不包含 | 找嘉宾、现场录制、平台代运营、保证播放量 |
| 验收方式 | 文件可打开、语句连贯、术语与逐字稿一致、时间戳到达对应段落 |

对应的采购问答不再写“提供全链路播客增长解决方案”，而写：

> **我们只有录音文件，可以外包哪一段？** 这项服务从已有分轨录音开始，包含剪辑、逐字稿、摘要和时间戳。客户仍负责主持、嘉宾与录音；若需要找嘉宾或现场录制，应选择另含这些环节的服务。

为这项虚构服务配两条测试题：

```text
匹配题：我们已经录好四集企业访谈，想找人剪辑并整理逐字稿，采购时应检查什么？
不匹配题：我们没有主持和嘉宾，希望找一家包办选题、邀约、现场拍摄的团队。
```

#### 验收

- 一位没参加过销售会议的人，只读交付卡，就能判断这两条需求哪条适合。
- 每个公开案例都能区分自家贡献、客户工作和第三方工作；无法披露的部分说明范围，不编客户名字。
- AI 回答若把“不含邀约”说成“包办嘉宾”，记录为错误描述；即使提到了品牌也不算成功。
- 合格咨询按事先规定的服务匹配条件统计，不能因为来自 AI 就放宽认定标准。

#### 一手资源

- [Google：有帮助、可靠、面向读者的内容](https://developers.google.com/search/docs/fundamentals/creating-helpful-content) — 学习怎样展示创作者、工作方法与原始贡献。
- [Google：组织结构化数据](https://developers.google.com/search/docs/appearance/structured-data/organization) — 核对组织名称、网址和相关身份资料；不代表标记后必获推荐。

</details>

<a id="playbook-creator"></a>

<details>
<summary>内容创作者：视频与播客如何配一份可核查资料？</summary>

**适用情形：** 你已经有视频、播客、采访或评测，但关键方法只在声音里，自动字幕容易错，读者找不到某个结论的出处。先做一条代表作，别批量生成几十篇重复摘要。

#### 具体动作

1. **选有原创工作的一集。** 记录谁做了什么、何时做、采用什么材料、结论适用范围；评测保留原始记录，采访区分受访者意见与已经核实的事实。

2. **校订字幕而非只上传转写结果。** 优先复核人名、产品型号、数字、否定词和专业术语。YouTube 支持上传字幕文件或手动编辑等方式，具体入口见其官方字幕指南。[字幕指南](https://support.google.com/youtube/answer/2734796?hl=en)

3. **给知识段落增加章节。** YouTube 手工章节从 `00:00` 开始，至少三个升序时间戳，每章至少 10 秒；发布后逐项点开核对。[章节规则](https://support.google.com/youtube/answer/9884579?hl=en)

4. **让主张回到证据。** 简介或配套笔记中列出“结论—方法—原始记录位置—限制”；有作者介绍时连接真实作者资料。ProfilePage 的主体应是与站点相关的单个人或组织，不能给任何文章随意套用。[作者资料文档](https://developers.google.com/search/docs/appearance/structured-data/profile-page)

#### 填好的教学示例：八分钟桌面收纳实验

以下节目与数据均为**原创教学设定**，不是已发布视频或真实实验结果。

```text
节目标题：给常用物品固定位置，真的能更快找到吗？
作者身份：本集实验的执行者；不自称行为科学专家
范围：同一张书桌、5 件物品、同一位参与者
方法：整理前后各做 5 次查找；保留每次计时与现场录像
教学设定结果：整理前 12/14/11/15/13 秒；整理后 6/8/7/5/9 秒
局限：样本只有一个人，且重复任务可能带来熟悉效应
```

章节可以这样写；所列时间点需与制作后的真实视频逐项核对：

```text
00:00 为什么要测查找时间
00:45 物品、计时方法和规则
02:10 整理前五次记录
03:20 怎样给物品固定位置
05:10 整理后五次记录
06:35 结果、熟悉效应和适用范围
```

配套证据表只需围绕实际主张：

| 主张 | 教学证据 | 可以说什么 | 不能说什么 |
|---|---|---|---|
| 本轮查找更快 | 两组各 5 个计时；均值 13 秒与 7 秒 | 这位参与者在这次任务中用时下降 | 所有人工作效率提升 46% |
| 固定位置是原因 | 只有前后观察，没有独立对照 | 可能解释之一，需继续检验 | 排除了熟悉与练习效应 |

#### 验收

- 字幕中的 10 个数字与原始记录一致；每个章节链接到对应论述，没有标题党跳转。
- 别人能从笔记找到计时规则和完整数值，重新计算均值。
- 用“这项实验能证明所有人都更高效吗”提问时，核查 AI 是否保留小样本限制。
- 转写、章节和作者资料改善的是可读性、定位和追溯；是否获得引用要另测。

#### 一手资源

- [YouTube：添加字幕](https://support.google.com/youtube/answer/2734796?hl=en) — 按实际视频语言上传或编辑，人工校对关键事实。
- [YouTube：视频章节](https://support.google.com/youtube/answer/9884579?hl=en) — 核对格式、时间和功能资格。
- [Google：作者资料页面](https://developers.google.com/search/docs/appearance/structured-data/profile-page) — 核对资料页适用范围，区分作者身份与文章本身。

</details>

<details>
<summary>多语言：翻译之前先核对市场、事实与题集</summary>

以下是本项目实操方法；平台技术规则只在明确引用处适用。

**1. 把市场事实从译文里拆出来。** 给同一条服务各写一张事实卡，分别记录语言、服务地域、币种、时间区间、可交付语言与排除项。上述播客教学例子可做 `zh-CN / 中国大陆 / 普通话逐字稿` 与 `en-SG / 新加坡 / 英文逐字稿` 两行；英文审听如果并未提供，就写不提供，不让翻译补出新能力。

**2. 各自找问题，再对齐意图。** 每个市场先收集 5 条真实咨询原话，标明来源；将“播客后期”和“podcast editing”放进同一个意图家族，但保留用户原始措辞。没有真实咨询时，用人工构造题练习并标明性质。请熟悉当地用法的人复核术语、单位与服务边界，再分别测试；不要拿两组不同题目的引用率直接比较语言效果。

**3. 有独立语言网页时检查双向对应。** Google 的 `hreflang` 指南要求列出自身与其他版本、使用完整 URL，并提供返回关系。下面是本项目自写示例，两个版本的 `<head>` 都放同一组链接；仅在页面确实存在、内容互为对应版本时使用。[Google 多语言版本指南](https://developers.google.com/search/docs/specialty/international/localized-versions)

```html
<link rel="alternate" hreflang="zh-CN" href="https://example.com/zh-cn/podcast-editing">
<link rel="alternate" hreflang="en-SG" href="https://example.com/en-sg/podcast-editing">
```

验收时同时检查语言切换、实际页面内容、返回标记和当地可用条件。`hreflang` 说明版本关系，不替代本地事实，也不能推出所有 AI 平台都按它选择引用。

</details>

<details>
<summary>展开：五个平台的 11 项官方资料、控制对照与操作清单</summary>

本页把 Google Search、Bing / Copilot、ChatGPT、Perplexity、Claude 分开学习。**同一个公司的搜索产品、模型训练、用户指定网址抓取、开发者 API，不能当成同一条收录渠道。**

核验日期：**2026-10-14**。以下 11 项精选均已打开并阅读所列官方正文；中文是导读，规则以链接中的当前原文为准。“平台明示”指文档明确表达；“练习”是本项目设计的学习任务，不代表平台保证效果。

#### 学习目标与先修

- 能区分“可抓取、可入索引、可作为答案来源、实际被引用、产生访问”五种状态。
- 能为目标平台单独检查入口、机器人权限、内容要求与可观测指标。
- 能说明一次答案观测的产品、日期、地区、语言及联网状态，避免拿 API 实验代替消费端结论。
- 先修：知道 URL、HTTP 状态码和 robots.txt 的基本含义。不熟悉时，先完成[技术基础](#technical)的前三项。

#### 必读 3 项

**1. Google：生成式搜索优化官方指南**

[Optimizing your website for generative AI features on Google Search](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)

**来源类型：官方技术指南｜难度：入门｜原文语言：英语，支持切换中文｜核验：2026-10-14｜状态：已读正文**

- **学什么：** Google 如何把已有搜索索引、检索增强生成和查询扩展用于 AI 搜索；为何有独特经验的内容、站点可访问性和清晰的信息结构仍是基础。该指南还分别讨论本地商家、电商、图片、视频和浏览器代理。
- **平台明示：** 页面需要被索引、可显示摘要，且站点未被 Search Console 的生成式 AI 控制排除。Google Search 不使用 llms.txt；没有必需的特殊 schema，也没有统一的“最佳切块长度”。
- **练习：** 选一篇现有文章，写出它独有的证据、读者问题、缺失的技术条件；把一个宽泛问题拆成三个研究子问题，再决定是补充原页还是确有必要新增页面。

**2. OpenAI：搜索、训练与用户请求机器人**

[Overview of OpenAI Crawlers](https://developers.openai.com/api/docs/bots)

**来源类型：官方机器人说明｜难度：入门至进阶｜原文语言：英语｜核验：2026-10-14｜状态：已读正文**

- **学什么：** `OAI-SearchBot` 用于 ChatGPT 搜索；`GPTBot` 涉及可能用于模型训练的抓取；`ChatGPT-User` 支持用户触发的访问。说明虽位于开发者文档站，正文明确涉及 ChatGPT 搜索。
- **平台明示：** 搜索与训练的 robots.txt 设置独立；允许搜索机器人不等于必须允许训练机器人。`ChatGPT-User` 不是自动网页爬虫，也不负责决定是否出现在搜索中；其用户请求可能不适用 robots.txt 规则。

- **验证边界：** 放行只解决访问条件，不能保证引用。禁用搜索机器人后仍可能出现导航链接；“完全没出现在任何答案中”不能由一条 robots 规则推出。

**3. Bing / Copilot：AI Performance 能测到什么**

[Introducing AI Performance in Bing Webmaster Tools Public Preview](https://blogs.bing.com/webmaster/2026/2/Introducing-AI-Performance-in-Bing-Webmaster-Tools-Public-Preview/)

**来源类型：官方产品公告与指标说明｜难度：入门｜原文语言：英语｜核验：2026-10-14｜状态：已读正文**

- **学什么：** Bing Webmaster Tools 的 AI Performance 如何呈现 Microsoft Copilot、Bing AI 摘要及部分合作集成中的引用。
- **平台明示：** 总引用数、每日平均被引用页面数、页面引用活动与 grounding queries 是不同指标；其中 grounding queries 仅为样本。聚合引用不表示答案中的位置、排名或权威程度。
- **练习：** 有站点权限时导出一个固定时间窗，选择三页，将“引用次数、实际站点访问、转化”分别记录；没有权限时先根据文档建立空表并写好指标定义。
- **验证边界：** 这是 2026-02-10 的公开预览公告，不能单凭公告推断每个账号当前拥有相同功能；覆盖部分 AI 产品，不能当成全网 AI 可见度。

**3. 百度 AI 搜索 / 文心：搜索 API 不能代替消费端实验**

**[百度搜索 API 文档](https://ai.baidu.com/ai-doc/AppBuilder/pmaxd1hvy)** · 中文 · 进阶 · 官方接口文档。

- **学什么**：阅读 `/v2/ai_search/web_search` 的输入、站点 / 时间筛选，以及返回的 URL、正文片段、相关性与权威性评分字段。
- **练习**：为 10 个真实用户问题保存返回来源；人工检查来源片段能否支撑答案，而非只看评分。另开记录观察百度消费端搜索与文心助手，不把结果混算。
- **边界**：返回 `authority_score` 不等于公开了评分算法；接入 API、被百度索引、被消费端 AI 引用是不同事件。该文档也不是“提交后保证推荐”的站长承诺。

**4. 腾讯元宝：阅读官方产品说明，核实实际引用**

**[腾讯元宝官方应用介绍](https://play.google.com/store/apps/details?hl=en_US&id=com.tencent.hunyuan.app.chat)** · 英文 · 入门 · 开发者发布的产品说明 · 核验时页面更新日期为 2026-09-08。

- **学什么**：产品介绍明确提及微信公众号、视频号等腾讯生态来源，可据此设计中文内容源观察。
- **练习**：选择 10 个问题，记录实际引用域名、原始作者、发布日期，以及引用的是全文还是转载；保留未找到来源的结果。
- **边界**：应用介绍是能力声明，未公开信源权重、收录时延或站长提交保证。不能从“支持公众号”推导出“发公众号必被推荐”；混元云 API 的检索也不能自动代表元宝。

**5. Kimi：读取搜索片段，并跟踪接口迁移**

**[联网搜索最佳实践](https://platform.kimi.com/docs/guide/best-practices-for-web-search)** · 中文 · 进阶 · 官方开发指南。

- **学什么**：区分 Basic 搜索、Pro 搜索和网页抓取；理解摘要、相关正文片段、全文的差异，以及站点 / 时间筛选。
- **练习**：为一个专业问题拟定明确的实体、时间和限定词，比较搜索片段是否保留关键前提；检查标题相符但正文不支持结论的情况。
- **边界**：文档强调相关性分数仅在同一次查询内有相对意义；API 的来源排序与消费端 Kimi 的最终回答不可混同。

**[旧 `$web_search` 工具与迁移说明](https://platform.kimi.com/docs/guide/use-web-search)** · 中文 · 进阶 · 官方迁移文档。

- **学什么**：资源地图必须记录接口生命周期，旧教程的代码不一定仍适用。
- **时间提醒**：截至 2026-10-14，原文写明旧内建工具**预计 2026-10-20 下线**，新接入推荐独立 REST 接口；这是计划日期，应在实际迁移时再次核查。

**6. 通义 / 千问：把“启用搜索”和“显示来源”分别检查**

**[阿里云百炼：联网搜索](https://help.aliyun.com/zh/model-studio/web-search/)** · 中文 · 进阶 · 官方开发文档。

- **学什么**：不同 API 协议启用搜索的方法不同；模型、搜索策略、来源返回与引用展示均需检查支持范围。

- **边界**：本文针对百炼 API，不是千问消费端的排名指南；在百炼运行其他厂商模型，也不等于复现那个厂商 App 的搜索系统。

每次记录这五组信息：

1. **测试条件**：时间与时区、平台、网页/App/API、界面显示的模型版本、地区/语言、登录与记忆设置；看不到的版本填未知。

3. **完整证据**：题目原文、回答全文、截图、每条引用的实际 URL，以及引用对应的句子。截图用于保留界面，全文用于检索复核。

| 状态 | 提及品牌 | 引用官网 | 支持引用判断 | 如何计数 |
| --- | --- | --- | --- | --- |
| 正常回答，提及拾页但只引第三方 | 1 | 0 | 留空 | 进入有效分母，官网引用不加分 |

| 回答说不适用，正确引官网限制 | 1 | 1 | 1 | 仍是准确引用，不需要夸奖产品 |
| 回答正常但没提品牌、没有搜索 | 0 | 0 | 留空 | 进入有效分母 |
| 页面超时，未取得回答 | 留空 | 留空 | 留空 | 留在计划表，进入失败率 |

**第四步：运行已经填好的文件。** [16 行模拟记录](examples/observation-demo.csv)可用表格软件打开。仓库中的 [汇总脚本](scripts/summarize_observations.py)仅用 Python 标准库、本地读 CSV，不联网、不调用模型。进入仓库目录执行：

```bash
python scripts/summarize_observations.py examples/observation-demo.csv
```

本脚本用于通用观察表，每份文件只保留同一平台、入口、地区与会话/搜索协议的前后观察。脚本会检查这些可选条件列，发现混组或缺失会拒绝汇总；多个平台分别导出 CSV，不能直接合算。先完成全部计划运行与人工标注；未完成项另报原因，不伪装成技术失败。中文观察课的两张 CSV 采用不同字段，需整理成通用观察表并补齐标注后统计，不能直接把 `not_run` 计划表交给本脚本。

结果应包含下面这些值（脚本还输出每题的引用分布）：

```text
[before] questions=4 planned=8 valid=7 errors=1
mention_rate=4/7 (57.1%)
citation_rate=2/7 (28.6%)
supported_answer_rate=1/7 (14.3%)
support_within_cited=1/2 (50.0%)
failure_rate=1/8 (12.5%)

[after] questions=4 planned=8 valid=7 errors=1
mention_rate=5/7 (71.4%)
citation_rate=4/7 (57.1%)
supported_answer_rate=3/7 (42.9%)
support_within_cited=3/4 (75.0%)
failure_rate=1/8 (12.5%)
```

**第五步：写出正确的结论。** 官网引用回答占有效回答的比例从 `2/7` 到 `4/7`，提高约 **28.6 个百分点**，相对增幅 **100%**。但它没有告诉你搜索量、真实曝光、访问量或成交量；只有四个问题，也不能写“全网 AI 可见度翻倍”。准确支持率还需独立报告，不能让错误引用混在“成功”里。

技术失败的真实输出未知。基线的引用比例按全部计划运行计算，可能介于 `2/8` 和 `3/8`；复测介于 `4/8` 和 `5/8`。这是缺失值的上下界，不是统计置信区间。扩大真实实验时按问题家族和时间检查波动，不把所有调用当独立样本。

**第六步：把引用和生意接起来。** 分开保留“固定题集记录”“可识别的引荐访问”“业务事件”三张表，只有可追踪的同一访问链才关联。下表是实施规格示例，不是平台自带的统一事件名称：

| 项目 | 自己定义的事件 | 什么才算完成 | 常见误计 |
| --- | --- | --- | --- |
| 内容网站 | `newsletter_confirmed` | 用户完成确认订阅 | 点了订阅按钮 |
| 小程序 | `booking_confirmed` | 预约记录创建成功且非测试单 | 展示了小程序二维码 |
| SaaS | `first_workspace_created` | 首个工作区创建成功 | 只访问登录页 |
| 桌面软件 | `first_successful_export` | 首次成功导出任务 | 下载了安装包 |
| B2B 服务 | `qualified_lead` | 按预先标准审核为有效需求 | 收到任何表单/垃圾线索 |

不能把所有 direct 流量算为 AI，也不能把网站到小程序跳转失败的人当成已成交。已有分析系统可以按自身事件定义实现；GA4 的关键事件与广告转化有不同产品定义，先读[官方说明](https://support.google.com/analytics/answer/13965727?hl=en)。

**本课验收**：能重算五个比率；保留那两次技术失败；找到被标为 `supported_citation=0` 的两行，并指出缺少原回答、引用句与来源正文，因此本模拟文件只能练计算，不能独立核实那些标签。解释为什么结果上涨仍不证明改稿导致增长。真实项目再补原始证据、未改页面组、同期营销活动、发布与抓取时间，才能进一步讨论原因。

#### 第一步：固定问题集合

先写业务问题，再选题。例如：“在中文、某地区、某产品入口的非品牌服务推荐题中，我的服务被合理推荐的比例是否变化？”不要先看哪些题表现最好，再倒推测试目标。

建议为每个查询建立一行：

| 字段 | 记录内容 |
| --- | --- |
| `query_id`、`family_id` | 稳定编号；相同意图的改写归入同一查询家族 |
| `query_text`、`query_version` | 完整原句和题集版本；评估中不静默改题 |
| 语言、目标地域 | 分别记录；中文问题不自动代表中国大陆使用场景 |
| 意图 | 事实查询、入门学习、比较、推荐、交易前核验、排错等 |
| 品牌属性 | 非品牌、自己的品牌、竞品；分别汇报 |
| 业务约束 | 预算、用途、受众、地区、规格和排除条件 |
| 正确答案依据 | 可核验事实、合适答案范围和不应出现的错误断言 |
| 权重与来源 | 权重是否相同；题来自真实公开需求、站内反馈或人工构造 |

保留一份开发题集用于调试，一份冻结的评估题集用于最终验证。题集必须有失败机会，包括你不适合被推荐、证据不足、事实需要更新的问题。人工构造题集只代表这些题，不能冒充平台全体用户需求的随机样本。

#### 第二步：把一次运行记录完整

同一个品牌在不同入口可能经历不同检索与生成流程。**API、网页产品、移动端、搜索模式、深度研究模式分别作为测试对象**；同名模型也不能默认结果可互换。

| 类别 | 最小记录字段 |
| --- | --- |
| 运行身份 | `run_id`、`query_id`、`family_id`、UTC 时间、展示时区、实验组、重复编号 |
| 产品入口 | 平台、网页/App/API、模式、产品可见版本、模型标识；不可见则写 `unknown` |
| 用户环境 | 登录状态、账号档位、地域、界面语言、提问语言、设备；不保存密码或个人敏感内容 |
| 上下文 | 是否新会话、历史消息、记忆或个性化状态；无法关闭则记录 |
| 检索状态 | 请求是否允许联网、是否实际观察到搜索、公开可见的搜索查询与来源；看不到内部过程时写 `unknown` |
| API 参数 | 可用时记录模型版本、temperature、seed、工具、系统提示；不支持的参数写 `not_available` |
| 输出与证据 | 完整回答、截图或原始响应、引用 URL、证据片段、标注版本与标注人 |
| 运行失败 | 超时、限流、连接错误、区域不可用、截断、解析错误及原始错误信息 |
| 内容状态 | 被测试页面的版本与发布时间；是否有抓取/索引/检索证据及时间 |

“模型回答了但没有推荐”“拒答”“完成回答但未触发搜索”都是需要保留的产品行为。网络失败、抓取中断、解析丢失则单列技术失败。不要只保存最满意的一次回答，也不要重试到出现目标品牌才算完成。

#### 第三步：先规定指标分母

以下定义用于本项目的固定题集实验。`N_plan` 是预先计划运行次数，`N_valid` 是取得可判读完整产品输出的次数；拒答、无引用、无推荐仍属于有效产品输出。技术失败不偷偷记为“未提及”，要报告失败数及其分布。分母为零时填 `NA`，不是 0%。

| 指标 | 分子 / 分母 | 判定与限制 |
| --- | --- | --- |
| 运行完成率 | `N_valid / N_plan` | 单列技术失败类型；若两组完成率差异大，不只比较剩余答案 |
| 正文提及率 | 正文明确提及目标实体的有效回答数 / `N_valid` | 统一别名、排除同名误识别；负面提及也计提及，但情感另记；引用列表出现域名单独计 |
| 推荐率 | 明确把目标列为适合该需求选项的回答数 / 预先标记为推荐意图题的有效回答数 | 明确否定、只作比较、不适用说明不算推荐；有条件推荐需满足预先标注规则 |
| 域名引用率 | 至少引用一次目标域名的回答数 / `N_valid` | 一次回答最多计一次；与品牌被提及不同；保留原始及规范化 URL |
| 引用份额 | 目标域名的去重引用实例数 / 全部域名的去重引用实例数 | 本协议一个实例为“回答×规范化 URL”；同回答同 URL 重复只计一次；涵盖整个题集，不能与其他工具不同口径硬比 |
| 关键事实正确率 | 经证据核对为正确的可核验断言数 / 全部被标注的可核验断言数 | 标签分正确、错误、证据不足；证据不足仍留在分母，另报占比；同时报告断言覆盖量与答题率，防止靠少答提高得分 |
| 引用支持精度 | 来源确实支持对应断言的“断言—引用”配对数 / 全部被检查配对数 | 打开来源检查，链接存在不算支持；若链接无法访问，标为未知并另报，未验证项不计成功 |
| 引用覆盖率 | 至少被一条或一组引用充分支持的需证据断言数 / 全部需证据断言数 | 没链接的断言仍在分母；与“有多少条引用”不同 |
| AI 来源会话占比 | 按固定来源规则识别的 AI 引荐会话数 / 同期全站可观测会话数 | 保存识别规则与未知来源；这不是答案点击率 |
| AI 来源会话转化率 | 至少发生一次指定业务事件的 AI 引荐会话数 / AI 引荐会话数 | 预先指定事件，例如有效咨询或支付；事件次数不能混作去重会话数 |

“来源支持”与“事实正确”分别标注：来源可能本身有错，答案也可能碰巧正确却没有引用支持。正文中“暂不建议选择某品牌”可以计提及，但不计正向推荐。

对推荐率再给一个**合理推荐率**：满足预先定义的需求约束、事实没有关键错误的推荐回答数，除以同一推荐题有效回答分母。这样可以避免奖励不合适的推荐。领域判断存在争议时保留理由，不把主观意见包装成事实标签。

对于缺失的技术失败，可给提及或引用的敏感性区间：最低可观测比例为成功次数除以 `N_plan`；最高可能比例为“成功次数＋技术失败次数”除以 `N_plan`。这不是统计置信区间，只说明未知结果可能造成多大影响。

**别把不同数据源的分母接在一起**

- 固定题集的回答数、平台真实展示量、分析系统的会话数是三个不同分母。
- 没有同一范围内的真实曝光和点击，就不能计算可靠的“答案 CTR”。不要用自己测的 100 次答案作真实用户点击的分母。
- 付费工具的 visibility、share of voice、authority 可能有不同题集、权重、去重、过滤或采样方式；先索取定义，再比较趋势。
- 识别不到来源的访问保留为未知。不能把所有 direct 流量都算给 AI，也不能把可识别的 AI 引荐当作全部 AI 影响。

#### 第四步：处理随机性与时间变化

以下是入门实验建议，不是保证统计显著的万能样本量。

1. **预先规定重复计划。** 小练习可用 12—24 道题，每题每条件至少 3 次，分布在多个时间窗口。预算不足时减少题量并注明探索性，不挑选最佳运行。
2. **分开两个问题。** 同一时间窗内重复观察回答随机性；跨日、跨周重复观察系统和网页变化。把二者混成一个平均数会掩盖原因。
3. **能控制时进行配对和随机化。** 离线实验在同一题、同一候选来源下比较 A/B，并随机顺序；需要研究上下文位置时单独设实验。线上网页改动通常无法同时随机展示两个已索引版本，不应伪称标准 A/B 测试。
4. **先按题或查询家族汇总。** 相同问题的 30 次调用不是 30 个独立用户问题。报告每题的重复分布、各意图平均和失败率，再按预先权重汇总。
5. **报告不确定性。** 报原始计数、百分点变化和区间。进阶可按查询家族做配对聚类 bootstrap；若跨日相关明显，还需考虑时间块。少量查询的区间不代表全市场不确定性。
6. **不要边测边挑停点。** 提前规定总样本、观察窗口、主指标和结束条件。大量测试中只挑一个增长结果，容易产生偶然发现；探索结论留到新题集和新时间窗验证。

温度设为零或固定 seed 也不能保证整个搜索产品不变：检索结果、模型服务、上下文和平台路由都可能变化。无法获得这些内部变量时，诚实标注为不可观测。

#### 第五步：设计能解释结果的实验

| 设计 | 能回答什么 | 主要限制 |
| --- | --- | --- |
| 固定来源、固定模型，单变量改写 | 文本改变是否影响这一生成设置的使用或引用 | 未测真实检索、索引和用户行为 |
| 本地检索—重排—生成全流程 | 改写是否在自己的完整流程中产生阶段间取舍 | 不是商业搜索私有算法 |
| 商业产品固定题集持续观察 | 特定入口与时间窗内输出是否变化 | 变化可能来自模型、索引、竞品、地域或个性化 |
| 改页面前后比较，并保留未改页面组 | 改动是否伴随相对变化，可减少部分时间混淆 | 需检查组间可比性、更新差异和共同趋势；仍不自动证明因果 |
| 随机分配的用户或页面实验 | 在随机化单位与实验条件成立时估计干预效应 | 平台与内容间可能相互影响，污染对照；搜索抓取通常不可控 |

先写假设：“为页面补充真实、相关且可核验的证据，是否改善指定题集的引用支持率？”避免一次同时改标题、事实、站点结构、外链和品牌宣传，再声称是某一个动作有效。

页面发布不是平台已读取。记录抓取和索引证据、合理等待窗口、同期发布与营销活动；仍未知时明确写“无法确认干预内容已进入被测产品”。没看到效果既可能是方法无效，也可能是干预尚未进入流程。

比较均值时也查看负面结果：更多引用是否伴随错误增加；推荐更多是否违背适用条件；访问更多是否缺少合格咨询。先报告变化，再讨论可能解释。

#### 扩展资源

**4. Ragas: Automated Evaluation of Retrieval Augmented Generation**

[原始论文](https://arxiv.org/abs/2309.15217) · [官方 Faithfulness 指标文档](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)

原文语言：英文｜难度：进阶｜证据类型：原始方法论文与作者工具文档｜核验日期：2026-10-14

**学什么：** 分离检索上下文、回答相关性和忠实性。Faithfulness 文档把回答中得到上下文支持的断言数除以总断言数，可帮助设计逐断言复核流程。

**边界：** 对上下文忠实不意味着事实在现实中正确；reference-free 也不意味着不需要人工核查。固定工具版本、评审模型与提示，并用自己语言和行业的人工样本校准。

**5. ARES: An Automated Evaluation Framework for Retrieval-Augmented Generation Systems**

[论文全文](https://arxiv.org/html/2311.09476v2)

原文语言：英文｜难度：研究｜证据类型：原始自动评估研究论文｜核验日期：2026-10-14

**学什么：** 阅读上下文相关性、回答忠实性、回答相关性的分别判断，以及用人工标注配合 prediction-powered inference 估计得分与区间的思路。

**边界：** 不应拿一个未校准的 LLM 裁判输出当作客观真值。ARES 的统计程序有特定条件；只让模型打分再取平均不等于已经实现其方法。

**6. Google：生成式 AI 报告发布与更新记录**

[2026 年 6 月官方公告](https://developers.google.com/search/blog/2026/06/gen-ai-performance-reports)

原文语言：英文｜难度：入门｜证据类型：平台官方发布记录｜核验日期：2026-10-14

**学什么：** 学会对官方资料也核对时间。公告已更新说明相关报告于 2026-08-31 全球推出，包含生成式 AI 展示的单独视图；这部分数据也计入总体表现。

**边界：** 不再沿用“AI 表现只能混在 Web、完全无法拆分”的旧说法。单独视图不表示所有可能的业务指标都可拆分；以当前报告文档和实际账号可见字段为准。

**7. Google Analytics：Conversions vs. key events**

[官方定义](https://support.google.com/analytics/answer/13965727?hl=en)

原文语言：英文｜难度：入门｜证据类型：平台官方分析文档｜核验日期：2026-10-14

**学什么：** 明确业务关键事件、广告转化、计数方式与归因窗口，避免只用页面访问作为最终成功标准。为有效咨询、试用或支付建立稳定事件定义。

**边界：** 本页“会话转化率”是明确口径的业务指标；平台 key event 与 Ads conversion 应按其产品定义使用。来源归因分配的是观察到的触点信用，不等于该来源造成了新增购买。

**8. AI in Search Reduces Publisher Referrals Without Improving User Experience: Experimental Evidence**

[2026 年原始预印本全文](https://arxiv.org/html/2608.18352v1)

原文语言：英文｜难度：研究｜证据类型：预注册随机现场实验预印本｜核验日期：2026-10-14

**学什么：** 查看 Google Search 的用户随机分组、真实行为测量、预注册与局限。该研究把外部访问与用户体验作为结果，有助于理解为什么品牌可见度、引用和引流不能互相替代。

**边界：** 干预的是实验条件下 AI 搜索功能的可用性，不是某个站点的 GEO 改写；结论不能推出“所有 GEO 策略都无用”或代表所有国家、设备和平台。

### 9. 怎样读真实研究，而不只抄一个涨幅？

实施案例告诉我们团队做过什么，研究则帮助检查某些普遍说法。这里将三类问题分开：哪些因素与可见度相关、用户是否点击、来源是否真的支持答案。

- [Pew：AI summaries and clicks](https://www.pewresearch.org/short-reads/2025/07/22/google-users-are-less-likely-to-click-on-links-when-an-ai-summary-appears-in-the-results/) — 浏览行为研究。学习为什么引用、点击和转化需要分开测量。

目标：能判断一条 GEO 建议由什么证据支持，并把研究改成自己能执行的小实验。以下 **3 项原始研究**均已读取，统一核验于 **2026-10-14**；它们记录特定时期与样本，不代表今天所有产品和语言的表现。后附 1 项中文服务商案例的待复核拆解，明确区分“网页确实这样说”和“项目效果已经被独立核实”。

这三项研究属于**行业观察或检索审计，不属于品牌实施增长案例**。研究能帮助建立假设和测量方法，但不能替代“某品牌改了哪些页面，留下哪些证据，结果怎样”的项目档案。

#### 必读：三个不同问题，三种证据

**1. 品牌声誉与 AI 提及：相关性值得研究，但不能直接当操作公式**

**[Ahrefs：Top Brand Visibility Factors in ChatGPT, AI Mode, and AI Overviews](https://ahrefs.com/blog/ai-brand-visibility-correlations/)** · 英文 · 进阶 · 供应商自有数据 / 观察性研究 · 页面标注 2025-12-12。

- **样本 / 方法**：75,000 个品牌；以 DR > 40、最高流量关键词月搜索量至少 800 等条件筛选，再从其 Brand Radar 的大量回答中统计品牌提及。
- **发现**：网页 / YouTube 品牌提及与 AI 可见性呈较强相关，页面数量的相关性较弱。
- **局限**：样本倾向已有一定规模的品牌；不同产品的提问池并不完全一致，且包含早期 AI Overview 数据作比较。大品牌、媒体曝光与被推荐可能共同受其他因素影响。
- **不能推导**：“多买提及一定提升推荐”“反向链接完全没用”。这是相关性研究，供应商工具的样本也不是全体用户问题。
- **练习**：用自己的 20 个品牌 / 竞品建立小表，按品牌规模分组，先检查相关是否仍存在。结果只作探索，不能当因果验证。

**2. AI 摘要与访问：被引用不等于获得点击**

**[Pew Research Center：Google users are less likely to click on links when an AI summary appears](https://www.pewresearch.org/short-reads/2025/07/22/google-users-are-less-likely-to-click-on-links-when-an-ai-summary-appears-in-the-results/)** · 英文 · 入门至进阶 · 独立机构浏览行为观察 · 发布于 2025-07-22。

- **样本 / 时间**：900 名美国成年人；2025 年 3 月浏览记录，68,879 次不同 Google 搜索；研究者于 4 月重新获取相同查询的结果页。
- **发现**：有 AI 摘要的访问中，传统结果点击比例为 8%，无摘要时为 15%；摘要链接的点击比例约 1%。
- **局限**：不是随机对照试验；有无摘要的查询类型不同，而且浏览记录与结果重抓存在时间差。不能说“AI 摘要必然让每个站点流量减半”。
- **练习**：将自己的指标分成提及、引用、访问和转化四层，检查哪层有真实数据。没有来源级点击数据时明确缺失，不用引用截图替代营收证据。

**3. 引用正确性：看起来有来源，也可能归因错误**

**[Tow Center / Columbia Journalism Review：AI Search Has a Citation Problem](https://www.cjr.org/tow_center/we-compared-eight-ai-search-engines-theyre-all-bad-at-citing-news.php)** · 英文 · 入门至进阶 · 原始检索审计实验 · 发布于 2025-03-06。

- **样本 / 方法**：20 家新闻出版商，每家 10 篇文章，测试当时的 8 个搜索产品，共 1,600 次查询。给定摘录，要求识别原文标题、出版商和 URL；人工判断正确性。
- **发现**：按研究定义，合计超过 60% 的回答包含错误，并观察到虚构链接、转载归因等问题。
- **局限**：这是新闻摘录找源任务，且使用当时版本；不能概括今天所有回答的错误率，也不是内容优化对引用增长的因果实验。
- **练习**：用 10 篇自己有权使用的文章做归因核查，区分“正确原文、转载、URL 错误、内容不支持、未回答”。别把搜到同一句话视为完成核验。

#### 扩展读法：给任何“增长案例”补齐这些字段

| 字段 | 应当回答的问题 |
| --- | --- |
| 研究对象 | 哪个平台、模型、地区、语言、登录状态、搜索模式？ |
| 分母与抽样 | 多少问题、页面、品牌、用户？样本如何选择，失败结果是否保留？ |
| 时间 | 采集何时开始与结束？是否跨版本、季节或平台更新？ |
| 干预 | 到底改了什么？是否同时改内容、发布、外链、品牌投放？ |
| 对照 | 有无随机分组、匹配页面或未干预问题？基线是否重复测量？ |
| 指标 | 统计提及、引用、正确归因、访问，还是收入？增幅是相对值还是百分点？ |
| 利益关系 | 作者是否销售相关工具 / 服务，客户是否允许披露，原始数据可否复核？ |
| 结论范围 | 数据直接支持什么？哪些只是作者解释或待验证假设？ |

值得加入地图的案例不必全部“成功”。无变化、下降、错误引用、迁移失败和反证都能帮助读者避免无效投入。只有漂亮截图、未披露分母或只给百分比而不交代基线的案例，先放待验证区。

#### 练习与验收

选择 10 对主题和基线表现相近的页面，预先写下单一改动、问题集合、主指标和观察时间；可以随机决定每对中哪页接受改动。固定平台 / 模式，对同一问题多次记录，保存完整输出与引用 URL；同时记录内容重新抓取、平台变化等干扰因素。

这是一份**探索性实验练习**，10 对页面不保证统计功效；没有足够样本或可靠对照时，只报告观察。验收报告须包含未改善样本、绝对计数、分母、前后变化、对照变化、替代解释和不可判断之处。不要把“发布后上升”直接写成“发布导致上升”。

#### 实验课 A：自己完成一次引用归因审计

**性质：本项目原创教学练习。** 由 Tow Center 的研究问题启发，下面的样本、表格和验收规则是教学设计，不是原研究的额外结果，也不保证复现原研究的错误率。

**准备材料**

选择 10 篇自己拥有使用权的公开文章。为每篇保存标题、作者、原始 URL、首次发布日期、修改日期和网页快照；记录是否有授权转载。不要只挑已经被 AI 引用的文章，否则会排除最难被找到的样本。

从每篇选一段有辨识度、没有直接包含标题和作者的短摘录。在普通搜索中检查能否找到原文，并记录结果。这一步用于描述检索难度，不把搜索引擎的答案当最终真相，真值仍是原始出版记录。

**执行步骤**

1. 选 3 个能联网的产品，记录消费端 / API、可见模型版本、地区、语言和搜索模式。
2. 使用统一提问：“请查找这段文字的原始文章，给出标题、原作者或出版方、发布日期与原始 URL；无法确认请说明。”接上摘录。
3. 每次使用新会话，不在前一轮告诉平台答案；在同一时间窗中完成一轮。
4. 另一天重复一轮。教学规模为 `10 篇 × 3 平台 × 2 轮 = 60 条记录`，不据此估计全网准确率。
5. 保存完整输出与引用列表。访问失败、没有开启搜索、平台拒答单列，不静默删除。
6. 打开引用页核对标题、归属和原文位置；相同文字可能来自转载，不能仅靠句子相同判为正确原始出处。

**标注表与计算**

| 记录字段 | 填写示例或要求 |
| --- | --- |
| `article_id / run_id` | 使用稳定编号，便于复核同一文章的不同轮次 |
| 平台与时间 | 记录到具体日期时间，注明时区 |
| 搜索状态 | 已确认搜索 / 未搜索 / 无法判断 |
| 返回出处 | 标题、出版方、日期、URL 分列 |
| 是否原始来源 | 原始发布 / 授权转载 / 未知转载 / 无法确认 |
| 内容支撑 | 支撑 / 部分支撑 / 不支撑 / 无法访问 |
| 最终标签 | 全部正确 / 部分错误 / 全部错误 / 未回答 / 执行失败 |

统一使用测量章节的运行口径：**有效输出**指成功执行并取得可判读输出，包含拒答、未给出处和明确表示不知道；网络错误、截断或解析丢失单列技术失败。运行完成率＝有效输出数 / 计划运行数。原始出处命中率＝原始 URL 与出版方均正确的输出数 / 有效输出数，未回答留在分母。另可报告“给出出处后的准确率”＝正确出处数 / 实际给出出处的输出数，但不能与命中率混用。全部指标同时列原始计数；分母为零填 NA。

**怎么采取下一步**

如果问题是品牌归属错误，检查自己的页面是否明确写出品牌、产品与组织关系；如果经常引用旧版，检查旧版与新版是否有清晰日期、更新说明和链接；如果引用转载，应检查原文是否可访问、有稳定 URL 和明确作者信息。这些是诊断方向，不是对某个平台机制的证明。

验收产物：60 条原始记录、10 篇真值表、标签定义、错误类型汇总、5 条人工核验说明。另一位读者应能从原始页面重新得到你的判断。出现分歧时保留分歧，不把模型“帮你判分”的结果直接当人工事实。

#### 中文实施案例待复核区

**[移山科技：儿童用品品牌 GEO 优化案例](https://www.geokeji.com/blog/children-product-brand-geo-optimization-case-study-2026-01-29)** · 中文 · 进阶 · 服务商原始自述，效果未独立核实 · 发布于 2026-01-29，正文核验于 2026-10-14。

**原文披露了什么**

服务商称其为匿名儿童用品品牌改写按年龄划分的选购内容、补充产品归属纠错信息，并按平台持续观察。文中披露监测 100 多个问题、采用自研系统，数据区间为 2025-12-11 至 2026-01-26；其报告品牌可见率从 8.48% 到 56.35%。这些是作者报告的事实主张，本项目未验证客户身份、原始答案或效果。

**证据状态：原文已读，效果未独立验证**

公开页没有提供可识别客户、完整问题集合、逐条回答、分母定义、对应改版页面与可靠对照。因而读者无法复算结果，也不能分离内容、分发、平台变化的贡献。文中对各平台内容偏好的解释同样不属于官方算法说明。

**本项目的复核练习**

以下是独立设计的审查步骤，不是替该案例补写未披露的实施细节：

1. **重新计算单位**：从 8.48% 到 56.35% 是增加 **47.87 个百分点**；相对增长约 **564.5%**。报告必须说明使用哪一种，不能把百分点写成百分比。
2. **先要分母再看倍数**：询问有效查询次数、问题数、重复轮数、平台权重与去重规则。一个问题重复问很多次与很多不同问题各问一次，不代表同样的覆盖。
3. **索取页面级证据**：至少给出若干原页、改版页、发布时间和被引用 URL；客户保密时可用脱敏内容快照，仍需让读者核查到底改了什么。
4. **核验错误纠正**：产品归属应来自真实品牌与产品资料。降低竞争品牌的正常推荐不等于纠正错误，不应将竞品曝光本身定义为“干扰”。
5. **分开事实与机制解释**：观察到某类页面被引用，只能支持这批问题中的引用事实；声称平台“更信任”某类内容，需要额外实验或官方依据。
6. **保留未成功的部分**：要求报告没有改善的问题、出现错误的回答和无法访问的来源。只保留最终命中截图会形成选择偏差。

当前缺口：仍需能公开核验品牌身份、实际页面改动、完整采样方法与结果的中文 GEO 实施案例。匿名服务商叙述可用于练习证据审查，暂不作为“照着做就有效”的实战证明。

### 10. 论文与开源实现：按研究问题选读

运营读者先读摘要、实验设置和局限；研究读者再看指标、代码与数据。阅读目标是把一个想法变成可被验证或否定的实验。

- **来源改写**：页面中哪种表达被改动，是否有真实事实支持。
- **检索链路**：研究是否包含重新检索、重排，还是只在固定上下文里比较答案。
- **评价对象**：测的是回答里的可见度、引用质量，还是用户行为。
- **迁移条件**：不同语言、行业、平台与时间能否沿用结论，需要哪些新验证。

#### 学习目标

读完后，你应能解释一项 GEO 技巧改动了哪一阶段、论文实际测量了什么，以及结论能推广到哪里；也能把论文中的想法转化为一个可以失败、可以复查的实验。

先区分四个问题：页面是否能被发现；进入候选集合后是否被检索和选中；进入上下文后是否被准确使用和引用；用户看到回答后是否访问或采取行动。只验证其中一个环节的论文，不能自动回答其余问题。

#### 先修知识与阅读顺序

- 能区分抓取、索引、检索、重排、生成、引用；不必先掌握模型训练。
- 能读百分比、百分点、分母、基线与对照组；不熟悉时先看测量与实验部分。
- 运营读者先读必读资源的摘要、实验设置、局限；研究读者再读公式、附录、代码与数据划分。
- 建议顺序：GEO 原论文 → SAGEO Arena → ALCE → 按问题选择 RAG、长上下文、电商和复现代码。

#### 必读三项

**1. GEO: Generative Engine Optimization**

[论文全文，2024 年修订版](https://arxiv.org/html/2311.09735v3)

原文语言：英文｜难度：进阶｜证据类型：KDD 2024 原始研究论文｜核验日期：2026-10-14

**学什么：** 阅读第 2—3 节的来源改写、候选来源、重复采样及可见度指标；理解引用相关字数和位置如何计分。

**边界：** 特定实验的可见度提升不等于商业平台的流量、推荐或收入提升；当时的在线验证不能代替今天的复测。新增数据和引语仍须真实、相关、可溯源。

**2. SAGEO Arena: A Realistic Environment for Evaluating Search-Augmented Generative Engine Optimization**

[论文全文，2026 年 8 月修订版](https://arxiv.org/html/2602.12187v2)

原文语言：英文｜难度：研究｜证据类型：KDD 2026 原始基准论文｜核验日期：2026-10-14

**学什么：** 阅读第 3、5 节，研究保留网页结构的检索—重排—生成流程，检查同一种改写在不同阶段是否产生相反效果。这是已核实的后续 GEO 基准。

**边界：** 其端到端指自建流程，没有完整复现商用搜索私有排序与用户行为信号；不能推出某种 schema 必然增加真实平台曝光。

**3. Enabling Large Language Models to Generate Text with Citations（ALCE）**

[原始论文](https://arxiv.org/abs/2305.14627)

原文语言：英文｜难度：进阶｜证据类型：EMNLP 2023 原始评估论文｜核验日期：2026-10-14

**学什么：** 分开评价流畅性、正确性和引用质量，理解“有链接”“来源支持这句话”“关键事实都有来源”三者的差异。

**边界：** 自动蕴含判断需要复核；来源支持回答不代表来源自身可靠。回答质量指标不能直接当作品牌商业可见度评分。

#### 扩展资源：按问题选读

**4. GEO 作者代码与 GEO-bench 数据入口**

[GEO-optim/GEO](https://github.com/GEO-optim/GEO)

原文语言：英文；代码为 Python｜难度：研究｜证据类型：作者开源实现与数据入口｜核验日期：2026-10-14

**学什么：** 对照 `src/run_geo.py`、`src/geo_functions.py` 和 `geval_prompts/` 检查改写与评分；README 提供 GEO-bench 数据入口。

**边界：** 旧服务和依赖未必可用。固定提交、记录替换项，并标注改编实验；不要在测试集反复选提示后又把它当作未见测试。

**5. SAGEO Arena 作者实现**

[happysnail06/SAGEO_Arena](https://github.com/happysnail06/SAGEO_Arena)

原文语言：英文；代码为 Python｜难度：研究｜证据类型：论文关联的作者实现｜核验日期：2026-10-14

**学什么：** 查看语料、优化、检索与生成配置，区分“只替换上下文”和“把改写文档重新送入检索”两种实验。

**边界：** 先确认数据许可、硬件和调用成本，再跑小子集；只重跑生成、未更新检索结果，不能称为端到端验证。

**6. E-GEO: A Testbed for Generative Engine Optimization in E-Commerce**

[论文全文，2026 年 7 月修订版](https://arxiv.org/html/2511.20867v2)

原文语言：英文｜难度：研究｜证据类型：原始数据集与实验预印本｜核验日期：2026-10-14

**学什么：** 阅读商品查询与候选评价协议，让测试题覆盖预算、用途、偏好和排除条件，理解有约束的推荐。

**边界：** 候选商品的排序提升不等于真实平台抓取、推荐或成交；跨域结论仍依赖数据与引擎设置，不能靠虚构商品卖点提高分数。

**7. Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks**

[RAG 原始论文](https://arxiv.org/abs/2005.11401)

原文语言：英文｜难度：进阶｜证据类型：NeurIPS 2020 原始机制论文｜核验日期：2026-10-14

**学什么：** 理解参数记忆与外部知识如何参与生成，区分“模型知道某事实”和“本次使用了某网页”。

**边界：** 这是具体检索增强模型的研究，不是所有商用产品的架构说明。不能从品牌出现反推它来自训练、实时检索或指定数据库。

**8. Lost in the Middle: How Language Models Use Long Contexts**

[原始论文](https://arxiv.org/abs/2307.03172)

原文语言：英文｜难度：进阶｜证据类型：TACL 原始受控实验论文｜核验日期：2026-10-14

**学什么：** 理解上下文位置与长度如何影响信息使用，借鉴“保持事实不变、只改变证据位置”的实验思路。

**边界：** 输入上下文位置不等于网页屏幕位置，旧模型结果须在新模型复测；不能据此推导“品牌写在网页第一句即可获推荐”。

#### 读论文时必须填写的证据卡

下面是本项目建议的阅读模板，不是任何论文的官方打分标准。

| 字段 | 必须回答的问题 |
| --- | --- |
| 研究对象 | 改网页正文、标题、结构、检索器、提示词，还是模型？ |
| 系统范围 | 离线固定候选／本地端到端系统／在线 API／面向用户产品？ |
| 输入分布 | 哪些语言、行业、题型、时间段和地域？品牌题与非品牌题是否分开？ |
| 基线和对照 | 与原文、随机改写还是强基线比较？还有哪些东西一起变了？ |
| 指标 | 名称、公式、分母、去重方法；是否包含真实用户？ |
| 统计单位 | 查询、查询家族、文档、用户还是调用？重复是否独立？ |
| 改善与代价 | 引用变多时，事实准确性、检索命中、成本或用户体验是否变差？ |
| 可复现性 | 数据与代码是否可取得？版本、提示、参数、失败样本是否公开？ |
| 有效范围 | 能支持什么结论？没有测哪些平台、语言、阶段或商业结果？ |

阅读顺序可从“结论→实验设置→指标→局限→方法”开始。遇到提升数字，先问分母与基线，再决定是否值得复现。预印本、作者代码和同行评审论文分别记录；发表状态不能替代对实验适用范围的判断。

#### 三个可做的练习

1. **拆解一个流行结论。** 从 GEO 原论文挑一个结果，写出实验条件与指标。将它改写为限定范围的中文结论，并举出一个该结果无法回答的问题。
2. **做最小机制实验。** 选 8—12 个问题和一组可公开使用的固定来源，只修改一个变量，例如把已有、可证实的结论改写得更清晰。对原文和改写运行配对重复测试，保留原文、改写、完整回答、引用与失败。注明这是离线机制实验。
3. **寻找反例。** 至少保存一个引用增加但事实准确性下降、或生成阶段得分增加但检索表现变差的真实实验样本；若没有发现，写“本样本未观察到”，不要制造反例。

#### 验收标准

- 能用自己的话区分“被检索”“被提及”“被引用”“被推荐”“带来转化”。
- 完成三张证据卡，至少包含原始 GEO 和一个后续基准。
- 能指出固定候选实验和商用平台观察之间至少两个缺失环节。
- 每项复现实验都有原始材料、版本记录、失败记录和可重算的指标。
- 结论能被数据否定，且没有把某一实验中的收益写成普遍承诺。

## 毕业练习：完成一个可复查的 GEO 项目

下面是本项目设计的学习作业。选一个自己有权限修改的真实页面；没有网站时，可先完成问题研究、现状审查与离线改稿，结果标为“未发布、未验证”。

| 步骤 | 具体怎么做 | 留下的材料 |
| --- | --- | --- |
| 1. 明确目标 | 写出用户、使用情境和要做的决定，例如判断某项服务是否适合自己 | 一句话项目目标与适用范围 |
| 2. 收集问题 | 从真实反馈整理需求，标记哪些是人为补充的假设；品牌题和非品牌题分开 | 有固定编号的题集与来源 |
| 3. 记录基线 | 在选定平台按相同条件重复观察；保存回答、来源及未出现品牌的样本 | 原始记录、条件与当前指标 |
| 4. 找一个缺口 | 对照页面与引用来源，确认是事实缺失、表达不清、技术障碍，还是尚无法判断 | 证据、改动假设与替代解释 |
| 5. 做有限修改 | 第一轮只选一类改动；事实不足先补证据，保存修改前后的版本 | 改稿单、差异、审核结果 |
| 6. 发布并记录 | 写清实际时间和地址，观察可获得的抓取或索引证据；未知则如实记录 | 发布日志与可观察状态 |
| 7. 按原口径复测 | 保留相同题集和条件；有条件时保留匹配对照页，同时记录平台变化 | 前后及对照的绝对计数 |
| 8. 复盘 | 说明改善、下降、无变化、未知各是什么，决定继续、回滚或换假设 | 一页结论与下一轮计划 |

**提交材料**：问题与事实表、改前改后内容、实际图像与来源、发布差异、完整观察记录、可重算结论。缺少网站权限时做离线改稿并明确未上线；没有增长也可以完成学习验收。

**不合格的交付**：只有“优化了权威性”等描述；只留表现最好的一次回答；只有百分比没有计数；把概念图当实测截图；把模拟数据写成客户成绩。
