# 🇨🇳 中文平台：豆包、DeepSeek、百度、元宝、Kimi、千问

> [GEO 实战手册](../../README.md) › 平台规则 › 中文

**国产 AI 怎么找资料、引用谁？官方能确认的写清楚，没公开的标为未知，然后教你自己测。**

| ⏱ 用时 | 👤 适合谁 | 📦 做完你手里有 |
| --- | --- | --- |
| 1–3 小时 | 目标用户在国内的品牌、商家、内容团队 | 六个平台的一手资料清单 · 一套可复查的中文 AI 观察流程（含 24 次运行计划 CSV） |

**先记住这 3 条**

1. 截至 2026-10-14，六家平台都**没有公开**站长推荐规则或排名公式。宣称知道“内部权重”的说法，先要证据。
2. 元宝官方应用介绍提到公众号、视频号等来源；百度、Kimi、千问（百炼）、豆包（火山引擎）开放了搜索 API，可以研究检索结构，但 API ≠ App。
3. 取证方法：同题、新会话、每题重复 3 次，保存回答和每条引用，“未测”不填 0。

先分清三层：**消费端助手 → 企业搜索 / 模型 API → 自建应用**。同一模型可以接入不同搜索源；API 的检索参数不能直接推导为 App 的引用规则。

## 必读：按平台阅读一手资料

### 1. 豆包：先认识公开的搜索服务

**[火山引擎官方联网搜索 MCP Server](https://github.com/volcengine/mcp-server/blob/main/server/mcp_server_askecho_search_infinity/README.md)** · 中文 · 进阶 · 官方开源实现 / README。

- **📌 要点**：当前 README 说明接入豆包搜索 Custom 版；公开网页 / 图片搜索、时间范围、限定站点、正文格式和查询改写等参数。适合观察“搜索输入—返回内容”这一环节。
- **🛠 动手**：阅读参数表，为同一个问题设计“全网、限定站点、限定时间”三组请求；说明每次只改变什么、要比较哪类来源。没有密钥也可以先完成实验设计。
- **⚠️ 不能推出**：这是开发者服务，不能据此宣称豆包 App 必然优先某平台，或给出“权威等级”的内部计算公式。
- **待补核**：[火山方舟联网搜索工具文档](https://docs.volcengine.com/docs/ark/web-search?lang=zh)在本次直接读取中只返回脚本外壳，未计入已核验正文资源；参数实施前需重新阅读当前文档。

### 2. DeepSeek：历史公告与当前 API 分开看

**[联网搜索上线官网公告](https://www.deepseek.com/news/v2-5-final/)** · 中文 · 入门 · 官方产品公告 · 发布于 2024-12-10。

- **📌 要点**：消费端联网搜索曾被作为独立产品能力发布，公告描述了复杂问题的多个关键词搜索。
- **🛠 动手 / ⚠️ 限制**：标出公告中的时间性语句，尤其“API 暂不支持搜索”只代表当时状态；不能把历史公告当成 2026 年所有 API 的能力说明。

**[Using the Responses API](https://api-docs.deepseek.com/guides/responses_api/)** · 英文 · 进阶 · 官方 API 文档。

- **📌 要点**：查兼容性表而非只看“兼容 OpenAI”的宣传。核验时该协议的工具表将内建 `web_search` 标为忽略，普通函数调用则是另一种能力。
- **🛠 动手 / ⚠️ 限制**：把实验记录中的“DeepSeek”补充为“入口、协议、模型、是否外接搜索”。这一页不能代表网页端、其他协议或第三方托管平台的行为。

### 3. 百度 AI 搜索 / 文心：搜索 API 不能代替消费端实验

**[百度搜索 API 文档](https://ai.baidu.com/ai-doc/AppBuilder/pmaxd1hvy)** · 中文 · 进阶 · 官方接口文档。

- **📌 要点**：阅读 `/v2/ai_search/web_search` 的输入、站点 / 时间筛选，以及返回的 URL、正文片段、相关性与权威性评分字段。
- **🛠 动手**：为 10 个真实用户问题保存返回来源；人工检查来源片段能否支撑答案，而非只看评分。另开记录观察百度消费端搜索与文心助手，不把结果混算。
- **⚠️ 不能推出**：返回 `authority_score` 不等于公开了评分算法；接入 API、被百度索引、被消费端 AI 引用是不同事件。该文档也不是“提交后保证推荐”的站长承诺。

### 4. 腾讯元宝：阅读官方产品说明，核实实际引用

**[腾讯元宝官方应用介绍](https://play.google.com/store/apps/details?hl=en_US&id=com.tencent.hunyuan.app.chat)** · 英文 · 入门 · 开发者发布的产品说明 · 核验时页面更新日期为 2026-09-08。

- **📌 要点**：产品介绍明确提及微信公众号、视频号等腾讯生态来源，可据此设计中文内容源观察。
- **🛠 动手**：选择 10 个问题，记录实际引用域名、原始作者、发布日期，以及引用的是全文还是转载；保留未找到来源的结果。
- **⚠️ 不能推出**：应用介绍是能力声明，未公开信源权重、收录时延或站长提交保证。不能从“支持公众号”推导出“发公众号必被推荐”；混元云 API 的检索也不能自动代表元宝。

### 5. Kimi：读取搜索片段，并跟踪接口迁移

**[联网搜索最佳实践](https://platform.kimi.com/docs/guide/best-practices-for-web-search)** · 中文 · 进阶 · 官方开发指南。

- **📌 要点**：区分 Basic 搜索、Pro 搜索和网页抓取；理解摘要、相关正文片段、全文的差异，以及站点 / 时间筛选。
- **🛠 动手**：为一个专业问题拟定明确的实体、时间和限定词，比较搜索片段是否保留关键前提；检查标题相符但正文不支持结论的情况。
- **⚠️ 不能推出**：文档强调相关性分数仅在同一次查询内有相对意义；API 的来源排序与消费端 Kimi 的最终回答不可混同。

**[旧 `$web_search` 工具与迁移说明](https://platform.kimi.com/docs/guide/use-web-search)** · 中文 · 进阶 · 官方迁移文档。

- **📌 要点**：资源地图必须记录接口生命周期，旧教程的代码不一定仍适用。
- **时间提醒**：截至 2026-10-14，原文写明旧内建工具**预计 2026-10-20 下线**，新接入推荐独立 REST 接口；这是计划日期，应在实际迁移时再次核查。

### 6. 通义 / 千问：把“启用搜索”和“显示来源”分别检查

**[阿里云百炼：联网搜索](https://help.aliyun.com/zh/model-studio/web-search/)** · 中文 · 进阶 · 官方开发文档。

- **📌 要点**：不同 API 协议启用搜索的方法不同；模型、搜索策略、来源返回与引用展示均需检查支持范围。
- **🛠 动手**：做一份配置卡：协议、模型、搜索开关、来源开关、引用格式；确认返回了可访问的来源，而不是仅凭回答自称“已经搜索”。
- **⚠️ 不能推出**：本文针对百炼 API，不是千问消费端的排名指南；在百炼运行其他厂商模型，也不等于复现那个厂商 App 的搜索系统。

## 扩展：中文平台值得研究但尚缺可靠答案的问题

- 每个平台在不同意图、语言、地区和登录状态下，实际引用哪些来源？需要分层抽样，不能用几个截图概括全站。
- 原创网页与转载页面被引用的差异是什么？需要保存首次发布时间、转载关系与原始链接。
- 更新内容后多久被重新读取？公开资料不足时，应报告自己的观测区间与未发生更新的样本。
- 消费端是否有公开站长控制、专属抓取说明、引用申诉入口？本页尚未建立完整、可验证的文档集合，欢迎贡献原始官方来源。

## 动手做：在 DeepSeek 与元宝记录一次可复查的中文搜索

目标：留下“这次回答了什么、用了哪些来源、来源是否支持说法”的证据。没有自己的项目，就用下面四道真实存在的 Notion 文档问题来练。（本节是操作课，不含平台实测排名。）

### 准备：只固定两个消费端入口

| 平台 | 本轮入口 | 先确认什么 | 一手资料能证明到哪里 |
| --- | --- | --- | --- |
| DeepSeek | [官方网页端](https://chat.deepseek.com/) | 登录状态、可见模型 / 模式、联网控件原文与状态 | [2024-12-10 官方公告](https://www.deepseek.com/news/v2-5-final/)确认当时网页端上线联网搜索；当前按钮和模式以你实际界面为准 |
| 腾讯元宝 | [官方网页端](https://yuanbao.tencent.com/) | 登录状态、可见模型 / 模式、搜索入口或联网控件 | [开发者发布的应用介绍](https://apps.apple.com/cn/app/id6480446430)声明可搜索公众号、视频号等来源；不披露这些来源的权重 |

以上链接于 **2026-10-14** 阅读核验。元宝应用介绍属于 App 能力描述，因此这次网页端是否展示同一能力仍要现场记录。**“元宝里选择 DeepSeek 模型”记为元宝的一种配置，不混入 DeepSeek 官网样本。**

### 第一步：用同一组问题起跑

没有自己项目时，用下面四道 Notion 文档问题练取证。它们针对真实公开文档，问题原文在各平台保持一致；每题开新会话，不先给参考答案或目标 URL。

```text
CN01：Notion 普通页面和数据库分别能导出为哪些格式？
CN02：把 Notion 工作区导出的文件重新上传，能立即恢复成原来的工作区吗？
CN03：我在 Notion 页面里看不到 Export，应该先检查哪些权限或设置？
CN04：Notion 导出的 HTML 是否能包含页面和段落评论？
```

做自己产品时，也固定“品类无品牌题、带品牌核实题、限制题、故障题”四类，分开汇总。不要拿“请推荐拾页”这种指定答案的问题测自然推荐。

### 第二步：每次运行都按同一顺序取证

1. 打开指定入口，记录浏览器语言、所在地区的粗粒度信息、登录与否；手机 App 则另建一组，记录版本。
2. 新建空白会话，截图输入前界面：必须看得到平台、模型 / 模式标签与联网设置。看不到模型版本就写“界面未显示”。
3. 如有明确联网开关，打开并记录按钮原文；如只有自动搜索模式，写“自动”；没有可见开关就写“未知”。不要把模型回答里的“我已联网”当设置证据。
4. 粘贴一道完整原题，等回答结束后保存全文。完整答复（包括正常拒答）记 `status=ok`；网络错误、额度不足等导致未生成完整答复的情况记 `technical_error`；尚未运行记 `not_run`。拒答可以在答案文件中另标“拒答”，不能当作技术失败移出有效回答分母。保留每次结果，不反复刷新到满意为止。
5. 截图回答正文及引用标号。来源面板需要展开才能看全时，再截一张；长回答分多张连续截图。
6. 逐个打开实际出现的引用，保存引用标题、跳转前 URL、最终 URL、完整主机名、作者与发布日期。打不开写“访问失败”，不悄悄换成搜索找到的另一页。
7. 为每条关键结论指出它所对应的引用；读原文，判为“支持 / 部分支持 / 不支持 / 无法访问”。平台给了来源并不等于每句话都有证据。
8. 每题每平台做 3 次独立新会话，合计 24 次，顺序轮换。三次只用于认识波动；没有重复出现也保留，不能挑最好截图汇报。

截图文件可按 `CN02-deepseek-web-r1-01-settings.png`、`02-answer.png`、`03-sources.png` 命名；隐藏账号昵称、头像和历史对话。来源正文不必整站抓取，保留判断所需的短摘录、段落位置与可访问链接即可。

### 第三步：复制这份空表，不把“未测”填成零

下载：[24 次运行计划 CSV](../../examples/china-runs-template.csv) · [引用记录 CSV](../../examples/china-citations-template.csv)。运行表已填好 4 题 × 2 平台 × 3 轮，状态均为 `not_run`；引用表含一条明确标注的格式示例，开始记录前删除该示例，不计入实测。

```csv
run_id,question_id,platform,entry,observed_at,region,ui_language,login,mode_label,search_setting,search_evidence,status,brand_mentioned,citation_count,answer_file,screenshot_files
CN01-ds-r1,CN01,DeepSeek,https://chat.deepseek.com/,,,,,,,,not_run,,,,
CN01-yb-r1,CN01,元宝,https://yuanbao.tencent.com/,,,,,,,,not_run,,,,
```

一次回答可能有多个引用，因此来源另存一张表；不要在一个格子里塞十个链接：

```csv
run_id,citation_id,answer_claim,cited_title,shown_url,final_url,hostname,original_author,published_at,support_status,source_excerpt,source_location
```

`citation_count` 计回答中实际展示的可区分引用；只有 `status=ok` 的完成答复才填实际观察值，没有引用填 `0`。`not_run`、`technical_error` 的结果字段留空。正文只有纯文本书名、没有可定位来源时另写备注，不冒充可点击引用。`hostname` 保留完整主机名，例如 `www.notion.com`。若引用公众号，`mp.weixin.qq.com` 只是共同托管域，还必须记录公众号作者；不能把所有公众号误当一个独立出版者。

### 第四步：用官方文档核对，不靠另一个模型投票

本轮对照页是 [Notion 官方导出说明](https://www.notion.com/help/export-your-content)。先完成自然问答，再读下表；不要把标准答案提前贴进测量会话。

| 题目 | 2026-10-14 官方页可支持的核对要点 | 典型错误判定 |
| --- | --- | --- |
| CN01 | 非数据库页面可导出 Markdown；完整页面数据库导出 CSV，子页面有 Markdown；页面也有 HTML 等导出方式 | 把所有对象都简化成同一种导出格式 |
| CN02 | 导出文件重新上传不能立即重建整个工作区 | 声称 ZIP 一键恢复全部工作区结构 |
| CN03 | Enterprise 工作区 / 团队空间可能禁用导出；访客需要页面或数据库的 Full access | 不检查角色就让所有用户去改管理员设置 |
| CN04 | HTML 导出可包含页面级、块级评论，含已解决和未解决评论 | 不加格式条件地说“评论永远不能导出” |

如果正文答案对、引用却不支持，分别记“答案核对通过”和“该引用不支持”；不要合成一个模糊的正确率。官方页将来改变时，保存原核对日期并更新要点。

### 第五步：把观察变成下一项内容工作

| 你实际看见的现象 | 合理的下一步 | 现在不能推出的结论 |
| --- | --- | --- |
| 三次均没引用目标官网 | 检查答案实际引用了谁，再审目标页是否回答该问题、能否读取 | 不能直接判定官网被平台封禁 |
| 引用了官网，但把旧价格当新价格 | 对照被引 URL、页面日期、可见正文与当前价格页 | 不能仅凭一句错话定位内部缓存机制 |
| 引用转载而非原作者 | 记录原始与转载关系、内容差异和首次发布日期 | 不能说多转载一定提升效果 |
| 元宝引用公众号、DeepSeek 引用网页 | 在本题集内比较事实完整性、来源独立性与引用支持度 | 不能宣称某平台固定偏爱某域名 |
| 给目标 URL 后能总结，自然问题不引用 | 把“直链阅读”另存为诊断样本，继续检查自然检索 | 不能把直链总结当自然可见性提升 |

这一课的验收是：24 次计划运行都能追溯到题目、配置、原回答和状态；每个关键结论有引用核查；失败与未知没有被删除。完成后你得到的是一份小样本观察报告，下一次只改一个真实的信息缺口，再按原题复测。
